# 設計メモ: 商品の属性のタグ(バックログ B9)

商品に「素材・シーン・機能・スタイル」などの属性を、**決まった語彙から選んだタグ**として持たせ、AI の候補の絞り込み・テーマとの合い具合・週の露出の偏りに使うための設計。

- 状態: **設計の案(2026-10-17)。コードはまだない。** 決めたのは「軸ごとの決まった語彙から AI に選ばせる」「語彙にない言葉は候補として出させ、人が足す」「メイン画像の tags と同じ言葉でつなぐ」の 3 つ(利用者と合意。HANDOVER 6.16)。それ以外は、この文書の案で、11 章の「まだ決めていないこと」を利用者と決めてから作る
- 関係する文書: [BIGQUERY.md](BIGQUERY.md)(商品の出どころ・レビューの要約とキーワード = 8 章)、[BACKLOG.md](BACKLOG.md) の 8 章(B5・B6・B7)、[PRINCIPLES.md](PRINCIPLES.md) の 6 章(判断は人、AI は補助)
- 例に出す語彙は、説明のための一般的な衣料の言葉。利用先の実際の語彙・商品は、ここにもコードにも書かない(利用先の環境で作る)

---

## 1. なぜタグを持つか

- いまの AI の商品選定は、ブラウザが全商品の名前・説明・カテゴリなどを JSON で渡し、テーマとの合い具合を Gemini が毎回読み取っている(`src/aiSelect.ts` の `productPayload`)。商品が数百点になると、プロンプトが大きく、遅く、選び方も毎回ぶれる。
- 「雨の日の通勤」「ギフト」のようなテーマに合う商品を、**先に機械で絞れる**材料がない(カテゴリと季節・天候適性だけ)。
- 週の配信で、同じような商品(例: ニットばかり・きれいめばかり)に偏っても、気づく手がかりがない。
- **自由なタグ(AI に好きに付けさせる)だと、言い換えでばらける**(「撥水」「防水」「雨に強い」「water-repellent」)。数えられず、絞り込みにも使えない。だから、**決まった語彙から選ばせる**。

## 2. 方針(結論の案)

1. **軸(素材・シーン・機能・スタイル …)ごとに、決まった語彙を持つ。** 語彙は表に置き、⚙ から人が直せる(コードに固定しない。利用先ごとに商品が違うため)。
2. **タグは「コード」で持ち、表示の言葉は語彙の表から引く。** コードは市場・言語によらず共通(`wool`、`commute`)。表示は日本語・英語を語彙の表に持つ。言い換え・表記ゆれを、語彙の「別名」で吸収する。
3. **AI(Gemini)に、商品の名前・説明・カテゴリ・レビューのキーワードから、語彙の中のコードだけを選ばせる。** 返答はコードで確かめ、語彙にないコードは捨てる。
4. **語彙にない言葉は「候補」として別に出させ、人が採用して語彙に足す**(AI に語彙を増やさせない)。
5. **人が直したタグは、AI が上書きしない。**(判断は人。PRINCIPLES 6 章)
6. **メイン画像にも、同じ語彙のタグを持たせる**(いまの自由な `tags` は残す)。商品とメイン画像を、同じコードで突き合わせる。
7. タグ付けは、B5(レビューの要約)と同じ仕組みで、**取り込みのときに、変わった商品だけ、時間の上限まで**行う。

## 3. 軸の案

| 軸(コード) | 何を表すか | 語彙の例(コード: 日本語 / English) | 1 商品あたり | AI で付けやすいか |
|---|---|---|---|---|
| 素材 `material` | 主な素材・生地 | `wool`: ウール / Wool、`cotton`: コットン / Cotton、`linen`: リネン / Linen、`down`: ダウン / Down、`leather`: レザー / Leather、`denim`: デニム / Denim、`synthetic`: 化学繊維 / Synthetic | 0〜2 | 高い(説明に書いてあることが多い)。**利用先の商品マスタに素材の列があれば、AI ではなくそれを使う**(9 章) |
| シーン `scene` | 着る・使う場面 | `commute`: 通勤 / Commute、`office`: オフィス / Office、`weekend`: 休日 / Weekend、`outdoor`: アウトドア / Outdoor、`travel`: 旅行 / Travel、`formal`: きちんとした場 / Formal、`home`: 家で / At home、`gift`: ギフト / Gift | 1〜3 | 中(推し量りになる。説明・レビューに根拠があるものだけにさせる) |
| 機能 `function` | 機能・扱いやすさ | `water_repellent`: 撥水 / Water-repellent、`warm`: 保温 / Warmth、`lightweight`: 軽量 / Lightweight、`stretch`: ストレッチ / Stretch、`breathable`: 通気 / Breathable、`washable`: 家で洗える / Machine-washable、`wrinkle_free`: しわになりにくい / Wrinkle-resistant、`packable`: 持ち運びやすい / Packable | 0〜3 | 高い(説明・レビューのキーワードに出やすい) |
| スタイル `style` | 見た目の印象・テイスト | `basic`: 定番 / Classic、`smart`: きれいめ / Smart、`casual`: カジュアル / Casual、`sporty`: スポーティ / Sporty、`minimal`: ミニマル / Minimal、`trend`: トレンド / On-trend、`premium`: 上質 / Premium | 1〜2 | 中(言葉だけだと推し量り。画像を見せると上がる見込み。11 章) |

軸を足す候補(利用者と決める): **対象**(メンズ / ウィメンズ / キッズ。利用先のマスタにあれば、それを使う)、**色の系統**(SKU の色から機械的に作れる。AI は要らない)、**価格帯**(価格から機械的に作れる)。
**季節・天候適性は、軸にしない**(いまの `season`・`weather` と、BigQuery の天気への反応 `lift_*` で持っている。二重に持たない)。

語彙の大きさの目安: 1 軸 **8〜20 語**。少なすぎると絞り込みが効かず、多すぎると AI の選び方がぶれ、人も管理できない。

## 4. 語彙と、タグの持ち方

### 4.1 語彙の表(案: `tag_vocab`)

| 列 | 中身 |
|---|---|
| `axis` | 軸のコード(`material` など。選択肢) |
| `code` | タグのコード(`wool`。軸の中で一意。英小文字と `_`。**一度使ったら変えない**。保存済みの商品・画像のタグが参照するため) |
| `label_ja` / `label_en` | 表示の言葉(画面は `t()` ではなく、この列を言語で選ぶ) |
| `aliases` | 別名(JSON の配列。「防水」「雨に強い」「water-resistant」など)。AI への指示と、候補の言葉を既存のコードに寄せるときに使う |
| `description` | 迷いやすい語の線引き(例: `smart` = オフィスでも着られる程度。`formal` とは分ける)。AI への指示に入れる |
| `markets` | 使う市場(空なら全市場)。市場で語彙を分けたいときだけ |
| `active` | 使うか(やめた語は消さずに外す。保存済みのタグを壊さないため) |
| `sort` | 並び順 |

軸そのもの(軸の一覧・1 商品あたりの上限)は、最初はコードに持ち、語彙だけを表にする案(軸を増やすのは、使い道のコードも直すときなので)。

### 4.2 商品のタグ(案: `products.attr_tags` と、そのもと)

- **案 A(先に作る案)**: `products.attr_tags`(text。JSON `{"material": ["wool"], "scene": ["commute", "office"], ...}`)、`attr_tags_basis`(作り直すかの目安。5 章)、`attr_tags_by`(`ai` / `human`)。`review_keywords` と同じく、JSON の文字で持つ。データの API・画面の読み方が、いまの作りのままで済む。
- **案 B**: 表 `product_tags`(`product_id`・`axis`・`code`・`source`(ai / human)・`confidence`)。SQL で「このタグの商品」「週の露出のタグの内訳」を数えやすい。B6 でサーバーが候補を絞るようになったら、こちらが向く。
- 案 A で始めて、B6 のサーバーでの絞り込みを作るときに、案 B に移す(または PostgreSQL の JSON の索引で足りるか確かめる)のがむだが少ない。**どちらにするかは、B6 の作りと一緒に決める**(11 章)。

人が直したとき: 案 A なら `attr_tags_by = 'human'` にして、AI は作り直さない(軸ごとに分けたいなら、軸ごとに持つ)。案 B なら `source = 'human'` の行を AI が消さない。

## 5. AI に語彙から選ばせる

### 5.1 いつ作るか

- B5(レビューの要約)と同じく、**BigQuery の取り込みの最後に、変わった商品だけ、時間の上限まで**(Cloud Run は応答のあとの裏の処理が止まりやすいため。残りは次に開いたとき)。順番待ちと時間の上限は、`summarize_reviews` と同じ形にする(順番が回ってきたときに上限を確かめる)。
- 作り直す目安 `attr_tags_basis` = 名前・説明・カテゴリ(`category_path`)・レビューのキーワード・**語彙の版**(語彙の表の最終更新)をつないだもののハッシュ。語彙を足したら、全商品が作り直しの対象になる(上限の中で少しずつ)。
- **レビューの要約と同じ呼び出しにまとめるか**: まとめると呼ぶ回数は減るが、レビューのない商品にもタグは要り、作り直す条件も違う。**別の呼び出しにする案**(11 章)。

### 5.2 指示の案

指示文は日本語で書く(CLAUDE.md の約束)。語彙は軸ごとに「コード: 日本語 / English(別名。線引き)」の一覧で渡す。

```
あなたは EC の商品の分類の担当。次の商品に、軸ごとに、下の語彙の中からコードを選ぶ。
- 選んでよいのは、語彙にあるコードだけ。合うものがなければ、その軸は空でよい(無理に選ばない)
- 商品の名前・説明・カテゴリ・お客さまのレビューのキーワードに根拠があるものだけを選ぶ。推し量りで選ばない
- 1 商品あたりの上限: 素材 2・シーン 3・機能 3・スタイル 2
- 語彙にないが、この商品を表すのに大事だと思う言葉があれば、new_terms に軸と一緒に書く(最大 3 個。コードは作らない)
返答は JSON だけ:
{"tags": {"material": ["wool"], "scene": ["commute"], "function": ["warm"], "style": ["basic"]},
 "new_terms": [{"axis": "function", "term": "静電気が起きにくい", "why": "説明とレビューに何度も出る"}]}

語彙:
(軸ごとの一覧)

商品: (名前)/ カテゴリ: (category_path)/ 説明: (description)/ レビューのキーワード: (good・bad の言葉)
```

### 5.3 返答の確かめ(コードで)

- 語彙にないコード・`active` でないコード・別の軸のコードは捨てる(B5 の `parse_summary` と同じく、形の合わない要素だけ捨て、残りは活かす)。
- 軸ごとの上限を超えたら、先頭から上限まで。
- 返答が JSON として読めない・`tags` がないときは、その商品を飛ばす(次の機会に作り直す)。
- 単体テストは、B5 と同じく `ccp.ai.generate` を偽物に差し替えて書く(`server/tests/test_review_summary.py` の形)。

## 6. 語彙にない言葉を、候補として出させ、人が足す

1. AI の `new_terms` を、表(案: `tag_candidates`。`axis`・`term`・`count`(出た商品の数)・`examples`(商品のコードを数件)・`first_seen`・`status` = `open` / `adopted` / `rejected`)に積む。同じ軸・同じ言葉(空白・大文字小文字をそろえて)は 1 行にまとめて数える。
2. ⚙ →「商品のタグの語彙」に、語彙の一覧と、候補(数の多い順)を出す。候補ごとに、人が選ぶ:
   - **語彙に足す**(コード・日本語・英語を人が決める。AI が案を出してよい)
   - **既存の語の別名にする**(例: 「雨に強い」→ `water_repellent` の `aliases` に足す)
   - **足さない**(`rejected`。同じ言葉は、次からは数えるだけで、画面の上には出さない)
3. 語彙を変えると語彙の版が変わり、5.1 の目安で、商品が少しずつ作り直される。
4. 変更は `events` に記録する(だれが、いつ、どの語を足したか。U のユーザーの記録と同じ考え方)。

AI に語彙を直接増やさせない理由: 増やし始めると、言い換えの語が並び、自由なタグと同じことになるため。

## 7. メイン画像の tags とのつなぎ方

- いまのメイン画像の `tags`(`hero_images.tags`)は、自由な言葉をカンマでつないだ文字(例: 「新作,秋,コーディネート,アウター」)。用途・季節・カテゴリ・雰囲気が混ざっていて、市場ごとに言語も違う。**この列は、いまの使い方(AI の画像選定・検索)のために、そのまま残す。**
- メイン画像にも、商品と同じ語彙のタグ(案: `hero_images.attr_tags`)を足す。対象の軸は **シーン・スタイル**(素材・機能は、写っている商品によるので、画像には付けにくい)。
- 付け方: まずは、画像の名前・説明・いまの `tags` から AI に語彙で選ばせる(商品と同じ指示)。いまの `tags` の言葉が語彙の別名に当たるものは、AI を呼ばずに機械で寄せてもよい。**画像そのものを Gemini に見せて付ける**と精度が上がる見込みだが、画像の読み込みの時間・費用を確かめてから(11 章)。
- 使い方: 配信カードで選んだ商品のシーン・スタイルのタグと、メイン画像のタグの重なりを数え、メイン画像の候補の並びの材料にする(AI の画像選定の前の絞り込み・並べ替え。いまは AI がテーマと自由な tags を読んで選んでいる)。

## 8. 使い道

### 8.1 B6: AI に渡す候補の絞り込み

- **テーマ → タグ**: 配信のテーマ(「雨の日の通勤」)から、AI に語彙のコードを選ばせる(`scene: commute`、`function: water_repellent`)。商品の数によらず 1 回の短い呼び出しで済む。人がテーマにタグを足し引きできるようにする(判断は人)。
- **タグで並べてから渡す**: 市場・在庫・季節で絞ったあと(BIGQUERY.md の 6 章)、テーマのタグとの重なりの多い順に並べ、上位 N 点だけを AI に渡す。**タグのない商品は落とさず、重なり 0 として後ろに置く**(タグ付けが終わっていない商品・語彙に合わない商品を、黙って候補から外さないため)。
- **1 点あたりを短く**: 商品の候補(`productPayload`)に、説明の代わりに(または短くした説明と一緒に)タグのコードを渡す。言葉ではなくコードなので、短く、ぶれない。
- サーバーで絞るとき(B6 の「候補を返す API」)に、4.2 の案 B(`product_tags`)か、JSON の索引かを決める。

### 8.2 テーマとの合い具合

- 選んだ商品ごとに「テーマのタグとどれが重なったか」を、AI の理由とは別に、機械で出せる(商品の行に小さく並べる。中ペインの、選定した商品の操作の場所。右端の商品情報は参照専用なので、そこにはタグを並べるだけ)。
- 重なりが 0 の商品を選んでいたら、「テーマと合う根拠がタグにない」と知らせる(止めない)。

### 8.3 週の露出の偏り

- 週(月曜始まり)・市場ごとに、配信に載せた商品(`delivery_products`)のタグを軸ごとに数える。例: スタイルの `smart` が 7 割、シーンの `outdoor` が 0。
- 週の画面(W)・露出バランス(ワイヤーフレーム 09・05)に、軸ごとの内訳を出す。**偏りの基準(何割を超えたら知らせるか)は、利用者と決める**。アラート(A)にするかも、あとで決める。
- 週の方針(マーケティングポリシーの販売系 `sales_policies`)に「今週はアウトドアを重点に」のような行があれば、タグで「重点が載っているか」を確かめられる(M の拡張。今週の方針の `target` にタグのコードを書けるようにするかは、POLICY_FORMAT.md の変更になるので、別に決める)。

## 9. B7(カテゴリの値)との関係

- **カテゴリは「何であるか」(商品の種類。利用先のマスタの階層 `category_path`)、タグは「どんな性質か」(カテゴリをまたぐ属性)。** 同じことを二重に持たない。カテゴリの段(アウター > コート など)の言葉を、タグの語彙に入れない。
- B7 でカテゴリを自由な文字(利用先の値のまま)にするなら、タグの指示には `category_path` をそのまま渡す(AI がカテゴリから素材・シーンを推し量る材料になる)。
- 利用先のマスタに、素材・対象・ブランドの系統など、**タグの軸と同じ意味の列があれば、AI に付けさせずに、その値を語彙に寄せて使う**(確実で、費用もかからない)。BigQuery の出力(BIGQUERY_EXPORT.md)に列を足すことになるので、合意してから。
- だから、**B7 で利用先のカテゴリ・属性の値の一覧をもらうときに、タグの軸に当たる列があるかも一緒に確かめる**(HANDOVER 6.16 の「B7 と一緒に決めると、むだがない」)。

## 11. まだ決めていないこと

- **軸**: 素材・シーン・機能・スタイルで始めるか。対象・色の系統・価格帯を足すか。利用先のマスタにある列で置き換えられる軸はどれか(B7 と一緒に)。
- **語彙**: 最初の版をだれが作るか(利用先のマーケター / 本番の商品の説明から AI に案を出させて人が絞る)。1 軸あたりの語数。市場で語彙を分けるか(コードは共通・表示の言葉だけ市場ごと、を案とする)。
- **持ち方**: 4.2 の案 A(JSON の列)か案 B(表)か。人が直したタグを、軸ごとに守るか、商品ごとに守るか。
- **呼び出し**: レビューの要約(B5)と同じ呼び出しにまとめるか、別にするか(5.1。案は別)。1 回にまとめて何商品ずつ渡すか(1 商品ずつ / 10 商品ずつ。速さと選び方の質を、本番の商品で比べる)。
- **画像**: メイン画像に、画像そのものを見せてタグを付けるか(時間・費用)。商品の画像も見せるか(スタイルの精度)。
- **使い道の基準**: 週の偏りを知らせる割合、テーマのタグに AI を使うか人が選ぶか、候補を AI に何点まで渡すか(BIGQUERY.md の 10 章と同じ問い)。
- **いまのメイン画像の `tags`**: 語彙のタグがそろったら、自由な `tags` を AI の画像選定に渡すのをやめるか(残すと、プロンプトが長いまま)。
