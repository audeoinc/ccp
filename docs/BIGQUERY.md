## 1. 前提(利用者に確かめたこと)

| 項目 | 内容 |
|---|---|
| データの出どころ | 商品マスタ・売上・在庫・レビュー・天気・アクセスは、すべて利用先の BigQuery にある。**こちらが本番のデータ** |
| 画像 | 別に扱う(この設計の対象外) |
| 件数 | 商品は全体で数百。AI の推論は SPU 単位と SKU 単位で分かれる(SPU なら少ない数百) |
| 更新の頻度 | 在庫は 1 時間に数回。それ以外は 1 日 1 回で足りる |
| 新しさ | 最新のデータで選定する必要がある。アラートは特に |
| 天気 | 過去の天気と売上の相関を、推論に使う。予報は、配信日との関連の強さとして使う。地点は**代表の 1 地点** |
| BigQuery への接続 | Workbench から、Python で、サービスアカウント(SA)を使って、接続の実績がある |
| BigQuery の SQL | 出す形は、こちらの都合に合わせて自由に書ける。BigQuery で Gemini の関数は**使えない** |
| 市場 | データは市場ごとに分かれているが、市場の列はない。BigQuery の出力に持たせられる |
| 動かし方 | デモなので、サーバーが起動している間だけ取り込めればよい |
| 気にしていること | **速さ**。AI に配信カードを作らせるのに、時間をかけたくない |

## 2. 方針(結論)

1. **AI の呼び出しのたびに、BigQuery を読まない。** BigQuery の問い合わせは 1 回に数秒かかり、下書き 1 回で Gemini を 6〜9 回呼ぶと、その分が積み重なる。
2. **CCP のサーバーが、BigQuery を直接読み、PostgreSQL に写す**(GCS は経由しない)。数百〜数千行なので、書き出しのジョブ・ファイルの管理を挟む利点がない。
3. **在庫は、BigQuery の更新を 1〜2 分ごとに確かめ、変わったら写す。** BigQuery の在庫そのものが 1 時間に数回の更新なので、選定のたびに BigQuery を読むのと比べて、遅れは最大 1〜2 分。ほかは 1 日 1 回(更新を確かめて、変わっていれば写す)。
4. **集計・相関の計算は、BigQuery の SQL で済ませる。** AI には、生の明細ではなく、商品ごとの数字と短い文を渡す(速く、判断がぶれない)。
5. **保存は、粒度と更新の頻度で表を分け、AI とアラートは、組み立てたビューを読む。**

```
[サーバーが起動している間]
BigQuery ──(Workbench の SA で読む)──▶ CCP のサーバー ──(DATABASE_URL のユーザーで書く)──▶ PostgreSQL
  起動したとき: 全部を取り込む
  1〜2 分ごと: 在庫の表の最終更新の日時を見る(無料)→ 変わっていれば取り込む
  定期的に:   ほかの表も、変わっていれば取り込む(1 日 1 回の更新に追いつけばよい)

[配信カードを作るとき]
PostgreSQL のビュー(数ミリ秒)──▶ 候補を絞る ──▶ 短い形で Gemini に渡す ──▶ 選定と理由
```

## 3. 接続と権限

- **PostgreSQL は BigQuery と直接やりとりしない。** BigQuery を読むのは CCP のサーバー(Python)で、PostgreSQL のアカウントに BigQuery の権限は要らない。
- サーバーの Google の認証は、いまも Workbench の SA(`server/ccp/creds.py` の `google.auth.default`)。Gemini を呼べているのと同じ仕組みなので、BigQuery も同じ SA で読める。
  - いまの Python が鍵ファイルを使っている(`GOOGLE_APPLICATION_CREDENTIALS` やコードでの指定)なら、`server/workbench.env` に `GOOGLE_APPLICATION_CREDENTIALS` を足す。
- 要る権限: 読む対象のデータセットの閲覧(BigQuery データ閲覧者)と、ジョブの実行(BigQuery ジョブユーザー)。
- 足すパッケージ: `google-cloud-bigquery`(`scripts/workbench.sh update` で入る)。
- `ccp.cli check` に、BigQuery への接続の確認(どの SA でつながったか・各表を読めるか)を足す。
- **作った(2026-10-17。B1)**: `server/ccp/bq.py`(出力の場所は環境変数 `BQ_SPU` / `BQ_SKU` / `BQ_SKU_STOCK` / `BQ_WEEKLY` / `BQ_FORECAST`、ビューなら `BQ_<名前>_WATCH`、ジョブのプロジェクトは `BQ_PROJECT`。見本は `server/workbench.env.example`)。`ccp.cli check` の「■ BigQuery」で、接続のアカウント、出力ごとの種類・最終更新・行数、仕様(BIGQUERY_EXPORT.md)の列が揃っているか、ビューなら問い合わせの試し(dry run。料金なし)を確かめる。**本物の BigQuery では、まだ確かめていない**(Workbench で `check` を実行してもらう)。

## 4. 表の形

### 4.1 考えた 3 つの形

数百〜数千行なので、どの形でも PostgreSQL の読み込みは数ミリ秒で、速さの差はほぼない。**更新のしやすさと使いやすさ**で選んだ。

| | 正規化した複数の表 | 1 つの大きな表 | SPU の行に、SKU を入れ子で持つ |
|---|---|---|---|
| 在庫の頻繁な更新 | ◎ 在庫の小さな表だけを書き換える | △ 大きな行を書き換える | × 入れ子をまるごと書き換える |
| SPU で選ぶ | ○ 集計が要る(ビューで済む) | △ 毎回まとめ直す | ◎ そのまま |
| SKU で選ぶ・アラート | ◎ 行をそのまま絞り込める | ○ | × 入れ子の中を探す |
| AI に渡す形 | ○ 組み立てが要る(ビューで済む) | △ SPU の情報が SKU の数だけ重複 | ◎ 渡したい形そのもの |

→ **保存は正規化(粒度と更新の頻度で分ける)、読むときは入れ子の形(ビュー)。** 両方の利点を取る。

### 4.2 保存する表

| 表 | 粒度 | 更新 | 中身 |
|---|---|---|---|
| `products`(SPU。いまの表に列を足す) | SPU | 1 日 1 回 | 在庫以外のすべて(マスタ・売上の集計・レビュー・アクセス・天気への反応) |
| `sku`(新しい表) | SKU | 1 日 1 回 | 在庫以外のすべて + 属する SPU |
| `sku_stock`(新しい表) | SKU | 1 時間に数回 | 在庫と、その時点 |
| `weekly_performances`(いまの表) | SPU × 週 | 1 日 1 回 | 週ごとの販売数・売上・週末の在庫(在庫アラートの販売のペースと、画面の推移に使う) |
| `weather_forecast`(新しい表) | 日付(代表の 1 地点) | 予報の更新に合わせる | 予報 |

列の詳しい定義は [BIGQUERY_EXPORT.md](BIGQUERY_EXPORT.md)。

- **在庫は、SKU の表(`sku_stock`)だけに持つ。** BigQuery の在庫は SKU 単位(利用者に確認済み)。SPU の在庫を別に取り込むと、取り込みのタイミングで SPU と SKU の在庫が食い違う。SPU に要る「在庫のある SKU の割合」「欠けているサイズ・色」も、SKU の在庫からしか出せない。
- **いまの `products` を、SPU として使い続ける。** 画面のあちこちが `products` を読んでいるので、作り直さずに済む。`products.stock` は、在庫を取り込むたびに、同じ取り込みの中で SKU の合計を書き込む(表と同時に書き換えるので、食い違わない)。
- SKU が 1 つの SPU にだけ属するので、結びつける表は分けず、`sku` に SPU のコードを持たせる。
- 時系列(週ごとの推移)は、AI には渡さない(集計した値だけを渡す)。いまの在庫アラートと画面の推移のために、`weekly_performances` だけ残す。

### 4.3 読むためのビュー(保存しない。読むたびに組み立てる)

| ビュー | 中身 | 使うところ |
|---|---|---|
| `spu_for_ai` | `products` に、最新の在庫から集計した値(在庫の合計・在庫のある SKU の数と全体の数・欠けているサイズや色)を付ける | SPU 単位の選定 |
| `sku_for_ai` | `sku` に、SPU の情報と最新の在庫を付ける | SKU 単位の選定、在庫のアラート |

在庫が変われば、ビューを読んだ時点で SPU の集計にも反映される。SPU と SKU のどちらで選ぶかは、どちらのビューを読むかの違いだけになる。

## 5. 取り込み(更新の検知と検証)

```
① BigQuery の表の最終更新の日時を見る(メタデータだけ。無料・一瞬)
② 前回から変わっていれば、問い合わせて行を取る
③ PostgreSQL の作業用の表に入れて、検証する
    - 件数が、前回と比べて極端に減っていないか(例: 半分以下なら止める)
    - 必須の列(コード・在庫 など)が空でないか
    - SKU がすべて、既知の SPU に結びつくか
④ 通れば、本番の表を 1 つのトランザクションで入れ替える(途中の状態を、画面や AI に見せない)
   通らなければ、前のデータのまま残し、画面とログに「取り込みを止めた理由」を出す
```

- **サーバーの起動時に、すぐ全部を取り込む**(止めていた間に古くなったデータで動かないように)。
- 取り込みは、サーバーの中で裏で動かす(FastAPI の起動時に始める)。サーバーが止まっている間は取り込まない(デモなので、それでよい)。
- 画面に「在庫: 14:32 時点」のように、BigQuery 側のデータの時点を出す(古いまま使われていないかを、人が確かめられるように)。
- 在庫を取り込んだら、サーバーで在庫のアラートを計算し直す(いまは、画面を開いたときに `src/alerts.ts` で計算している)。

## 6. AI への渡し方

- **候補を先に絞る**(PostgreSQL で数ミリ秒): 配信カードの市場・在庫あり・季節で絞る。SKU 単位は行が多いので、特に効く。
- **1 点あたりを短くする**: いまは JSON で項目名を毎回付けて渡している(`src/aiSelect.ts` の `productPayload`)。表の形にすると、同じ内容で文字数を大きく減らせる。
- **同じ書き出しを使い回す**: 下書き 1 回で 6〜9 回呼ぶので、商品の一覧を毎回同じ形でプロンプトの先頭に置けば、Gemini のキャッシュ(同じ書き出しのプロンプトが速く・安くなる)が効く見込みがある。**利用先のモデル・設定で効くかは、未確認。**
- いまはブラウザが全商品を読み込んでプロンプトを組み立てている。絞り込みはサーバーに「候補を返す API」を足して行う(ブラウザに全件を送らない)。

## 7. 天気の使い方

| 何を | どこで | 理由 |
|---|---|---|
| 過去の天気と売上の相関(天気への反応) | BigQuery の SQL で、1 日 1 回 | 数字の計算は、AI より SQL のほうが速く、正確。SPU ごとではデータが少ない商品は、カテゴリの値で補う |
| 配信日との関連の強さ | CCP のコードで、下書きを作るときに(数ミリ秒) | 「商品の天気への反応」×「配信日の予報」で、強・中・弱を決める。配信日が先で、予報が当てにならないほど弱める |
| 最終的な判断と、選定の理由 | AI | 「配信日は最高 28℃ の予報。この商品は暑い日に売上 +30%(強)」のような短い文を、材料として渡す |

天気への反応の定義(合意済み。しきい値は、商品の性質に合わせて調整してよい):

| 条件 | 定義 |
|---|---|
| 暑い日 | 最高気温 25℃ 以上 |
| 寒い日 | 最高気温 10℃ 以下 |
| 雨の日 | 降水量 1mm 以上 |

- 値 = (その条件の日の 1 日あたり販売数 ÷ それ以外の日の 1 日あたり販売数)− 1。+0.3 なら、売上 +30%。
- 期間は過去 365 日。計算に使った日数を、確からしさとして一緒に持つ。

## 8. レビューの要約

BigQuery で Gemini の関数を使えないので、**CCP の取り込みのときに、Workbench から Gemini で作る**(いまの Workbench で、すでに Gemini を呼べている)。

1. BigQuery は、SPU ごとに、件数・平均・最新のレビューの日時・直近のレビューの本文(最大 20 件ほどを 1 つの文字列につなげたもの)を出す。
2. CCP は、件数と最新の日時が前回から変わった SPU だけ、要約を作り直して `products.review_summary` に保存する。
3. 最初の 1 回は全件(数百点)なので、数分かかる見込み。裏で動かし、終わるまで AI は平均・件数だけで判断する。

### 8.1 追記: よく出る言葉と、コピーに使える声(2026-10-16。利用者の要望。**未合意**。バックログ B8)

マーケターは、コピーの案を作るときに、ユーザーのレビューのコメントも参考にしている(利用者の記憶。確かめる)。要約だけでは、ユーザーが実際に使った言葉が残らないので、次も持つ。

| 持つもの | 中身 | 使い道 |
|---|---|---|
| よく出る言葉・言い回し | SPU ごとの上位(20〜30 ほど)。言葉・件数・良い / 悪い / どちらでもない の別 | 商品情報に並べる。AI のコピーの依頼に「ユーザーがよく使う言葉」として渡す |
| 短い引用 | 良い声・悪い声を、数件ずつ。1 件は短く(1 文ほど)、個人を特定できる情報を除く | マーケターが、言い回しの参考にする。AI の理由に「どの声をもとにしたか」を書かせる |

**案(決めること)**

- **どこで数えるか**: 直近 20 件の本文(いまの `review_texts`)だけでは、よく出る言葉の数としては少ない。
  - 案 A: BigQuery の SQL で、全件のレビューから数えて、列で出してもらう(英語なら、単語・2 語の組の分け方は SQL で書ける。言語ごとに分け方が違うので、国を足すときに見直す)。
  - 案 B: CCP の取り込みで、要約と一緒に Gemini に「よく出る言葉と、短い引用」を JSON で出させる(BigQuery 側の変更が要らない。ただし、材料は直近 20 件)。
  - まずは案 B で試し、足りなければ案 A に進む、が速い。案 A にするときは、[BIGQUERY_EXPORT.md](BIGQUERY_EXPORT.md) に列を足す(SQL を書く人と合意してから)。
- **持ち方**: `products` に、よく出る言葉(JSON の配列 `[{term, count, sentiment}]`)と、引用(JSON の配列 `[{text, sentiment, rating}]`)の 2 列を足す。作り直す条件は、要約と同じ(件数と最新の日時が変わった SPU だけ)。
- **画面**: 商品情報(参照専用)に、言葉を件数つきで並べ、引用を数件出す。コピーを作るタブから、その商品の言葉・引用を見られるようにする。
- **AI**: コピー・見出しの依頼に、載せる商品の「よく出る言葉」(良いものの上位数件)を短く渡す。引用は、AI にそのまま写させない(ユーザーの文をそのまま広告に使わないため)。
- 個人を特定できる情報(名前・メールアドレス など)は、引用に残さない(BIGQUERY_EXPORT.md の ※3 と同じ考え方。取り込みの側でも、念のため除く)。

## 9. 引っ越し用のパックとの関係

BigQuery から取り込むようになると、`products`・`sku`・`sku_stock`・`weekly_performances`・`weather_forecast` の正しい出どころは BigQuery になる。
**パックを取り込むとき(`import-pack`)は、これらの表を置き換えない**ようにする(本番の Cloud Run のデモ用の商品データで、上書きしないため)。
配信カード・メモなど、CCP の中で作るデータは、これまでどおりパックで持ち込める。
