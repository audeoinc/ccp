## 2. 結果(R)でできたこと

画面の言葉で書く。詳しくは [BACKLOG.md](BACKLOG.md) の R1〜R10 の行。

- **計画と結果は、同じ画面の表と裏**(R8)。ヘッダーの題名の横の **[計画 | 結果]** で切り替える。
  - 絞り込み(国・チャネル・種別・ステータス)、期間の送り、**月 / 週 / 一覧** のツールバーは、表裏で共通。切り替えても、期間・見せ方・絞り込みはそのまま、ボタンの位置も動かない。
  - 結果の面だけの操作(まとめ方・CSV の書き出し・結果の取り込み・取り込みの見本)は、計画の面の「CSV で書き出す」の場所に、差し替わって出る。
  - 管理系(テンプレートの管理・言語・開いたとき自動で下書き)は、ヘッダー右の **⚙** のメニュー。
- **結果の面の見せ方**(R5・R9)
  - 月: カレンダーの日ごとに、売上・開封率(アプリはタップ率)・前年比。左の線が、前年より上なら緑、下なら赤。
  - 週: 日ごとに、**クリックを重ねたプレビュー(ヒートマップ)** と主な数字。1 週間の配信で、どこに載せた何が押されたかを比べる。
  - 一覧: 表。配信 / テーマ / テンプレート / 商品 でまとめられる。前週比・前年比。
- **詳しい結果はフロート**(R6・R9)。どの見せ方でも、配信を押すと開く。
  - 上に主な数字(開封率・クリック率・売上・注文・送った数・前年比)。
  - 下に「クリックを重ねたプレビュー | リンクごとのクリックの表 | 次に生かすメモ・商品の売れ方・採用した AI の案」。
- **計画と結果の行き来**(R10)。面を切り替えずに、フロートを上に重ねる。閉じると元に戻る。
  - 配信カードの「結果を見る」→ 結果を重ねる(閉じると配信カード、面は計画のまま)。
  - 結果のフロートの「制作の詳細」→ 配信カードを重ねる(閉じると結果、面は結果のまま)。
- **過去の配信と比べる**(R11・R12)。詳しい結果のフロートの下。同じ国・チャネルで「同じテンプレート / 同じテーマの種類」の、この配信より前の 3 / 5 / 10 回の平均と、数字(開封率・クリック率・売上・1 通あたりの売上)と、位置ごとのクリックの割合(メイン画像・ボタン・商品の枠の何番目か)を比べる。過去の配信のヒートマップを並べ、押すとその結果に切り替わる。
- **テーマの種類**(R12)。値下げ / セール / 新作 / 会員向け / 季節の特集 / 再入荷 / その他。結果の面の「AI でテーマの種類を分ける」で AI が分け、詳しい結果・配信カードで直せる。決まるまでは言葉から推し量った種類(「推定」)。
- **AI の振り返り**(R13)。比べの数字から、良かったこと / 悪かったこと / 次に試すこと と根拠の強さを AI が書く。保存せず、1 行ずつ「メモに採用」で次に生かすメモに足す。
- **比べる**(R15。利用者の「人が絞り込んで並べ、その並びを AI が評価する」という指摘で作った)。結果の面の見せ方の 4 つ目。テンプレート・テーマの種類・配信名(とツールバーの絞り込み)で絞り、直近 5 / 10 / 20 回を古い順に並べ、ヒートマップと「配信 × 数字・位置」の表で比べる。「並べた配信を AI で評価する」で並び全体を AI が評価し、最新の配信のメモに採用できる。
- **これまでの学び**(R14)。配信カードの題名の下の帯。同じテンプレートか同じテーマの種類の、過去の配信の次に生かすメモ(新しい順に 8 件まで)。帯が出ている間は、AI の案の依頼に learnings として渡す。
- **結果の取り込み**(R1)。CSV(列: `delivery, date, sent_at, recipients, opens, clicks, orders, revenue, last_year_revenue`)。配信は、配信名と配信日で探す。

## 3. データ

テーブル **`delivery_results`**(`server/schema.json` の末尾。Postgres では `delivery_results`)。配信ごとに 1 行。
反映(デプロイ)すると、サーバーが最初に DB につないだときに、足りないテーブル・列を自動で作る(`data_api._ensure_schema`)。手で migrate しなくてよい。

| 列 | 中身 |
|---|---|
| `delivery_card_id` | 配信カード(消すと、結果も消える) |
| `sent_at` | 送った日時 |
| `recipients` / `opens` / `clicks` / `orders` | 送った数 / 開封(アプリは通知のタップ)/ クリックした人 / 注文 |
| `revenue` / `last_year_revenue` | 売上 / 前年の同じ時期の売上(前年比に使う) |
| `products` | 商品ごとの結果。JSON の配列 `[{productId, clicks, units, revenue}]` |
| `links` | 商品以外のリンクのクリック(延べ回数)。JSON `{hero, buttons: [..], other}`。`buttons` は、**プレビューの上から順**のボタン |
| `notes` | 次に生かすメモ(配信カードの「これまでの学び」に出る) |

配信カードには、列 **`theme_type`**(テーマの種類のキー。`src/themeTypes.ts`)を足した。

- **いまの数字はすべてダミー**。本番は、2026-10-14 より前に送った配信 18 本に、決まった計算で入れた(配信 ID を乱数の種にしているので、何度作っても同じ)。サンプルデータ(`src/mock/seed.ts` の `deliveryResults`)も同じ考え方。
- 本番の週ごとの商品の売上(`weekly_performances`)は 9/28 の週まで。10 月の配信では「その週の販売の増減・在庫の週数」が出ない(サンプルデータでは出る)。
- **ダミーの過去の配信**: 本番は、2026-10-14 より前に送った US の配信(テンプレートと商品が入った 10 本)を、1〜5 週前にも送ったことにして 50 本足した(テンプレート・テーマは同じ、商品とメイン画像は入れ替え。その週は確定)。作った配信の ID は、作った人の手元(scratchpad の `past_created.json`)にしかないので、消すときは「10/14 より前・US・同じ名前の配信が 5 週分ある」ものを目安にする。サンプルデータも同じ考え方(`src/mock/seed.ts` の「過去の配信」)。
- 本番の過去の配信のうち 5 本に、次に生かすメモの見本を入れた。本番のテーマの種類は、まだ AI で分けていない(すべて「推定」)。結果の面の「AI でテーマの種類を分ける」を押すと分かれる(実際の AI を呼ぶ)。
- 商品のクリックは、上の枠ほど多くなるように作った(位置で比べたときに、傾向が見えるように)。数字はダミーなので、AI の振り返りは、もっともらしいだけで中身はない。

## 4. 設計の判断と、その理由

| 判断 | 理由 |
|---|---|
| 結果は、配信カードの表に列を足さず、別のテーブルにした(メモも結果のテーブル) | 配信カードの表は、W のメンバーもよく触る。ぶつからないように。結果は、あとから取り込むもので、配信カードとは書く人・時期が違う |
| リンクの位置は、プレビューの部品に付けた印(`data-link="hero" / "button" / "push"`、商品の枠の `data-item-key`)を、描いたあとに測って求める | テンプレートごとに座標を持たなくてよい。テンプレートを足しても、そのまま重なる |
| ボタンは「プレビューの上から順」の番号で結果と対応させる | ボタンの ID はテンプレートの中にあり、取り込む側(配信の仕組み)からは見えない。順番なら、配信の仕組みの「リンク 1・2…」と合わせやすい |
| ヒートマップの濃さは、**いちばん押されたリンクに対する相対** | 全体に対する割合だと、どのリンクも同じような色になり、全体が赤く見えた(利用者の指摘) |
| 計画と結果は「表と裏」。ツールバーは共通 | 同じ配信を、送る前と後で見ているだけ。別ページだと、切り替えでボタンの位置がずれ、期間も引き継がれなかった(利用者の指摘) |
| 月のカレンダーは、計画と結果で同じ部品(`Calendar`)。変えるのは、配信の箱の 2 行目(時刻・国 / 数字)と色(状態 / 前年比)だけ(2026-10-16) | 別々に作っていたため、外枠・マスの高さ・箱の並び・チャネルの示し方がそろわず、同じ配信だと気づきにくかった(利用者の指摘)。デザイン方針の 3-1・8-3 |
| カレンダーの配信は、メールは左の線、アプリは角の丸い枠(2026-10-16) | アイコンだけでは、ぱっと見で区別しにくかった(利用者の指摘)。色は状態・前年比に使っているので、形で分けた(4 案から利用者が選んだ) |
| 詳しい結果は、ページではなくフロート。一覧の右ペインはやめた | 右ペインは付属の情報に見え、縦に長くて読まれない。計画の面の配信カード(フロート)と操作をそろえる(利用者の指摘) |
| 計画と結果の行き来は、フロートを重ねる。面は切り替えない | 「作ったときはどうだったっけ」「結果は?」は、ちょっと確かめたいだけ。閉じたら元の場所に戻りたい(利用者の指摘) |
| 過去との比べは、商品ではなく「何番目の枠か」で比べる。テーマの種類で比べるときは、位置の比べを出さない | 同じテンプレートなら枠の位置が同じなので、回をまたいで比べられる。テンプレートが違うと、同じ番号の枠でも大きさ・場所が違う |
| テーマの種類は、配信カードの列にした | 結果がまだない、計画中の配信でも使う(これまでの学びを集めるため) |
| AI の振り返りは保存せず、採用したものだけをメモに入れる | AI の案は保存しない、という約束に合わせる。残るのは人が選んだ学びだけ |
| 学びを AI に渡すのは、`askAgent` が、依頼の種類(suggest_ / select_)を見て加える(`setActiveLearnings`) | チャットの履歴(withChat)と同じ形。下書きを作る関数の一つ一つを変えなくてよい |
| ツールバーの見せ方の切り替え(月 / 週 / 一覧 / 比べる)は、枠で囲んだひとかたまりにし、週の見方はラベル付きで外へ。右は区切りの線のあとに操作。結果の面の操作は「データ」のメニューに | 切り替えと操作が同じ見た目で並び、比べるを使ったあと、週に戻る場所がわからなかった(利用者の指摘) |
| 結果の面の操作は、ツールバーの決まった場所に `createPortal` で差し込む | ツールバーは App が持つ(計画と共通)。結果の画面の部品は、結果の画面のファイルに置いたままにしたい |
| Power Apps 版を廃止し、ソースも削除した(2026-10-16)。`src/generated/` の名前は、いったん残した(同じ日の名前の変更で、`src/models`・`src/data` に移した) | 利用者の決定。clone したときに Power Platform の環境と連携されないように(`power.config.json`・`.power/` を削除)。`src/generated/` の名前を変えると、画面の 60 近いファイルの読み込みが変わり、W のメンバーの作業とぶつかるため、中身だけ差し替えた |
| 名前(`cr854_…`)・選択肢の数(588230000 など)・参照の書き方(`@odata.bind`)をやめ、DB と同じ読みやすい名前と、文字の値にした(2026-10-16) | 利用者の希望(Power Apps の痕跡をなくす)。DB の列は、もとから読みやすい名前だったので、画面・API をそれに合わせ、名前の変換をなくした。選択肢は、数より文字のほうが、DB・ログ・CSV を見てもわかる |

## 6.5 利用先の Workbench での運用(2026-10-15)

チームメンバーが、利用先の Vertex AI Workbench でアプリを動かしている(`f03c9e2` で、Jupyter の中継 `/proxy/8081/` の下でも動くようにした)。
