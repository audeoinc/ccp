# 要件: 機能の公開・非公開を管理する(MVP から FULL まで)

相談: 2026-10-28、利用者と要件の相談相手のセッション。
もとにした資料: `docs/FEATURES.md`(2026-10-28 の main)。**画面を動かしての確かめはしていない**ので、入口の数・規模は目安。

## 1. 目的

- MVP を作り、**実際の担当者・利用者に使ってもらう**。リリースの版ごとに、使える機能を絞りたい。
- MVP の水準: **一通り企画が作れて、制作への引き渡しの材料が作れる**。より便利な AI の機能は要らない(利用者)。
- そのために、**使える機能を管理する機能**を作る。公開・非公開を、できるだけ細かく制御したい。

## 2. 決めたこと(利用者)

| 項目 | 決めたこと |
|---|---|
| 版と公開の関係 | **版は定義だけ**(どの機能がどの版に入るかの目安)。**実際の公開・非公開は、機能ごとに設定する** |
| だれに効くか | 一般の利用者は、その環境の設定どおり。**開発者だけは、すべて見える** |
| 非公開の見せ方 | **完全に隠す**(「近日公開」などの印も出さない) |
| MVP の AI | **「AI で全体を下書き」だけ MVP に入れる**(2026-10-28)。部品ごとの AI・まとめて作るなどは v2 |
| 配信カード | **シンプルだけを残す。詳しい配信カードは消した**(2026-10-28)。切り替えの対象ではなく、コードから外す |
| MVP のチャネル | **メールとアプリの両方**(2026-10-28) |
| どこで止めるか | **画面だけ**(サーバーの API では止めない) |

## 3. 管理機能の作り(相談の相手の案。担当が決める)

- **機能の一覧はコードに 1 つ**(例: `src/features.ts`)。機能ごとに ID・大 / 中 / 小の親子・版・前提(この機能を使うのに要る機能)・説明を書く。下の 5 章の表が、その中身の案。
- **公開の設定は DB**(例: 表 `feature_settings`。ID ごとに公開 / 非公開)。環境ごと(本番・Workbench)に別々に持つ。設定がない機能は「非公開」(新しく足した機能が、黙って出ないように)。
- **管理の画面**: ⚙ の「開発・管理」に「使える機能」。大 / 中 / 小の木で並べ、行ごとに公開・非公開を切り替える。上に「版を選んで、まとめて当てる」(版はあくまで、まとめて切り替える近道。当てたあとも 1 行ずつ変えられる)。
- **親子と前提**: 親を非公開にすると、子もすべて隠れる。前提の機能が非公開なのに公開にしようとしたら、知らせる(例: 「AI で全体を下書き」は「テンプレートを選ぶ」と「商品を選ぶ」が前提)。
- **入口はすべて共通の判定を通す**: ボタン・メニュー・右クリック・ディープリンク・キーの操作・AI のチャットの返事・「？ 聞く」の答えなど、機能の入口を出す所で、必ず `isOn('ID')` を通す。ディープリンクで非公開の画面を開こうとしたら、ふつうの画面で開く。
- **開発者**: ユーザーに「開発者」の印を付ける(例: `users.is_developer`)。開発者には、非公開の機能も出す。開発者が非公開の機能を見ているときは、小さく「非公開」の印を付ける(開発者が、一般の人の見え方とまちがえないように)。開発者が一般の人の見え方を確かめるための「一般の人として見る」の切り替えもあるとよい。
- **データは消さない**: 非公開にしても、データはそのまま。公開に戻せば、元のまま見える。
- 管理機能そのものの規模: **大**(一覧・DB・管理の画面・判定・開発者の印は中くらいだが、すべての入口に判定を入れて回る作業が大きい。下の表の機能ごとに順に入れていく)。

## 4. 版の定義(目安)

| 版 | ねらい | 主な中身 |
|---|---|---|
| **MVP** | 企画が作れて、制作に渡せる | カレンダー(月・週・一覧)、キャンペーンと配信カード(シンプル。**メールとアプリ**)、**AI で全体を下書き**、テンプレートを選ぶ、文言・画像・商品を手で入れる、プレビュー、配信カードの承認、渡すもの(制作指示・担当・締め切り・素材)、制作のページ(写しを見る・要素のコピー・企画の見本の HTML) |
| **v1** | チームで運用が回る | 週のレビューと確定、やり取り・タスク・ピン、変更の履歴、アラート(在庫など)、商品の詳しい情報、複製・取りやめ、CSV・PDF の書き出し |
| **v2** | AI で速く作る | 部品ごとの AI(案・指示して直す)、テーマの案、商品・画像の AI の選定、制作指示の AI、まとめて作る・週の枠、AB テスト・案から選ぶ、キャンペーンのまとめて承認 |
| **v3** | 結果を次に生かす | 結果の面(月・週・一覧・詳しい結果・比べる)、結果の取り込み、振り返り、効果、学びのカード、商品別 |
| **FULL** | すべて | テンプレートの管理と編集、画像のライブラリの管理、方針・決まりの編集、制作の HTML の編集と AI の手直し、開発へのリクエスト、外部広告 など |

## 5. 機能の分類と公開の順番

**開発規模**は、その機能を「切り替えられるようにする」手間(入口を探して判定を入れ、隠したときに画面が崩れないようにする)。

- **小**: 入口が 1〜2 か所で、ほかの機能と絡まない(ボタンやメニューの項目を隠すだけ)
- **中**: 入口が数か所ある、または隠すと画面の並びが変わる・前提の確かめが要る
- **大**: 面・見せ方・ペインごと隠す、またはほかの機能の表示や確かめに絡む(隠したときに、ほかの画面も直す)

版の「常時」は、切り替えない土台(非公開にできない)。

## 6. 規模のまとめ

| 規模 | 数(おおよそ) | 主なもの |
|---|---|---|
| 大 | 8 | 管理機能そのもの、結果の面、アプリの配信、AB テスト、週の確定、学び、アラート、テンプレートの管理 |
| 中 | 約 25 | 制作の面、送る前の確かめ、AI の下書き、やり取り・ピン など |
| 小 | 約 60 | ボタン・メニューの項目 1 つずつのもの |

作る順番のおすすめ: ⓪ シンプルな配信カードに、MVP の前に要る機能を移す(新規作成・アプリの開く画面と送る相手・utm の表示)→ ① 管理機能の土台(一覧・DB・管理の画面・判定・開発者の印)→ ② MVP で隠すもの(v1 以降の機能)に判定を入れる → ③ 詳しい配信カードを消す(残りの※の機能を移すか、要らないと決めてから)→ ④ 版を上げるたびに、その版の機能を公開する(コードはもう入っているので、設定を変えるだけ)。
**②が最大の作業**。MVP で隠す機能が多い(上の表の v1〜FULL のすべて)ので、MVP のための作業は、実は「MVP 以外のすべての入口に判定を入れる」こと。
