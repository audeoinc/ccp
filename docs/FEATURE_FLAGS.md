# 要件: 機能の公開・非公開を管理する(MVP から v4 まで)

相談: 2026-10-28、利用者と要件の相談相手のセッション。
もとにした資料: `docs/FEATURES.md`(2026-10-28 の main)。**画面を動かしての確かめはしていない**ので、入口の数・規模は目安。

## 1. 目的

- MVP を作り、**実際の担当者・利用者に使ってもらう**。リリースの版ごとに、使える機能を絞りたい。
- MVP の水準: **一通り企画が作れて、制作への引き渡しの材料が作れる**。より便利な AI の機能は要らない(利用者)。
- そのために、**使える機能を管理する機能**を作る。公開・非公開を、できるだけ細かく制御したい。

## 2. 決めたこと(利用者)

| 項目 | 決めたこと |
|---|---|
| 版と公開の関係 | **版は機能のまとまり**。機能の版は管理の画面で付け替えられる。**公開は版ごとにまとめて行い、機能ごとに「止める」「先に出す」で上書きできる**(2026-10-29 に変えた。はじめは「版は定義だけ、公開は機能ごと」だった。3.1) |
| だれに効くか | 一般の利用者は、その環境の設定どおり。**開発者だけは、すべて見える** |
| 非公開の見せ方 | **完全に隠す**(「近日公開」などの印も出さない) |
| MVP の AI | **「AI で全体を下書き」だけ MVP に入れる**(2026-10-28)。部品ごとの AI・まとめて作るなどは v2 |
| 配信カード | **シンプルだけを残す。詳しい配信カードは消した**(2026-10-28)。切り替えの対象ではなく、コードから外す |
| MVP のチャネル | **メールとアプリの両方**(2026-10-28) |
| どこで止めるか | **画面だけ**(サーバーの API では止めない) |

## 3. 管理機能の作り(相談の相手の案。担当が決める)

> **段 ① の作り(2026-10-29 に作った。UI 1)**
> - **機能の一覧は `src/features.ts` が正**(大 = `area.*`、中 = `area.*.*`、小 = 下の 5 章の ID。版・規模・前提 `requires`・日本語と英語の名前)。5 章の表は、これに合わせて直す。
> - **公開の設定は表 `feature_settings`**(`feature_id` ごとに 1 行、`enabled` 1 / 0、`changed_by`)。大・中の行も持てる。**行のない機能は、`feature_id = '*'` の行の値**。`'*'` はサーバーが起動のときに「公開」で入れるので、段 ① を入れても、いまの見え方は変わらない。管理の画面で**版を当てると、全部の機能の行を書き、`'*'` を非公開にする**(これで「設定がない機能は非公開」が効く。そのあと足した機能は、黙って出ない)。import-pack では取り込まない・消さない(`pack.py` の `ENV_ONLY`。本番と Workbench で別々)。
> - **判定は `isOn('ID')`**(`src/featureFlags.ts`。部品の中は `useFeature`)。常時はいつも公開、「開発者だけ」は開発者だけ。親(中・大)が非公開なら子も非公開。前提は判定に入れず、管理の画面で知らせるだけ。設定を読む前・読めないときは公開として扱う。知らない ID は出す。
> - **開発者は `users.is_developer`**(1 = 開発者。⚙「ユーザーと承認グループ」の「開発者」の列で、開発者か管理者だけが付け外す)。開発者には非公開の機能も出し、入口の横に小さい「非公開」の印(`FeatureBadge`)を付ける。**「一般の人として見る」**は、開発者にだけ「あなた」のメニューと管理の画面に出す(ブラウザごとに覚える)。
> - **管理の画面**は ⚙ の「開発・管理」の「使える機能」(`src/FeaturesManager.tsx`)。いまは、開発者か管理者だけが変えられる(ほかの人は読むだけ)。
> - 段 ① では、どの入口にも判定を入れていない(段 ② で入れる)。

- **機能の一覧はコードに 1 つ**(例: `src/features.ts`)。機能ごとに ID・大 / 中 / 小の親子・版・前提(この機能を使うのに要る機能)・説明を書く。下の 5 章の表が、その中身の案。
- **公開の設定は DB**(例: 表 `feature_settings`。ID ごとに公開 / 非公開)。環境ごと(本番・Workbench)に別々に持つ。設定がない機能は「非公開」(新しく足した機能が、黙って出ないように)。
- **管理の画面**: ⚙ の「開発・管理」に「使える機能」。大 / 中 / 小の木で並べ、行ごとに公開・非公開を切り替える。上に「版を選んで、まとめて当てる」(版はあくまで、まとめて切り替える近道。当てたあとも 1 行ずつ変えられる)。
- **親子と前提**: 親を非公開にすると、子もすべて隠れる。前提の機能が非公開なのに公開にしようとしたら、知らせる(例: 「AI で全体を下書き」は「テンプレートを選ぶ」と「商品を選ぶ」が前提)。
- **入口はすべて共通の判定を通す**: ボタン・メニュー・右クリック・ディープリンク・キーの操作・AI のチャットの返事・「？ 聞く」の答えなど、機能の入口を出す所で、必ず `isOn('ID')` を通す。ディープリンクで非公開の画面を開こうとしたら、ふつうの画面で開く。
- **開発者**: ユーザーに「開発者」の印を付ける(例: `users.is_developer`)。開発者には、非公開の機能も出す。開発者が非公開の機能を見ているときは、小さく「非公開」の印を付ける(開発者が、一般の人の見え方とまちがえないように)。開発者が一般の人の見え方を確かめるための「一般の人として見る」の切り替えもあるとよい。
- **データは消さない**: 非公開にしても、データはそのまま。公開に戻せば、元のまま見える。
- 管理機能そのものの規模: **大**(一覧・DB・管理の画面・判定・開発者の印は中くらいだが、すべての入口に判定を入れて回る作業が大きい。下の表の機能ごとに順に入れていく)。

### 3.1 版を付け替える・版ごとに公開する・機能ごとに止める(2026-10-29 利用者と決めた)

どの機能をどの版で出すかは、これから協議して変わる。そこで、**版の付け替えも、公開も、作り直しなしで管理の画面から変えられる**ようにする。段 ① の作り(上の囲み)から変えるところがある。

**決めたこと**

| 項目 | 決めたこと |
|---|---|
| 版の付け替え | 各機能の版は、コード(`src/features.ts`)の値を**はじめの値**とし、**管理の画面で付け替えられる**(DB に持つ)。協議の結果は、画面で版を変えるだけ。コードの値と違う機能には「付け替え済み」の印を出し、コードの値に戻せる |
| 版ごとの公開 | **版を 1 つのまとまり(グループ)として、公開 / 非公開を切り替える**(例: 「V1 を公開する」)。公開すると、その版の機能がまとめて見える(公開漏れがない)。あとで版に足した・付け替えた機能も、その版が公開なら見える |
| 機能ごとの上書き | 機能ごとに 3 つから選ぶ: **版に従う**(ふつう)/ **止める**(版が公開でも隠す。不具合のとき)/ **先に出す**(版が非公開でも、その機能だけ見せる) |
| 見えるかどうか | 機能の上書きがあればそれに従い、なければ版の公開に従う。常時はいつも公開、「開発者だけ」は開発者だけ、開発者にはすべて見える(これまでどおり)。親が非公開なら子も非公開(これまでどおり) |
| 止めている印 | 版の一覧に「V1: 公開(1 つ止めている)」のように、止めている・先に出している数を出す(戻し忘れを防ぐ)。行にも「止めている」の印と理由 |
| 前提の機能 | 止めた機能を前提にしている機能も見えなくなる・使えなくなるときは、止める前に知らせる(例: アラートを止めると、ヘッダーのアラートの件数も隠れる) |
| 記録 | 版の付け替え・版の公開・止める・先に出す・戻すを、だれが・いつ・**なぜ**(止めるときは理由を書く)行ったかを残す |
| データ | 止めても、データは消さない(これまでどおり) |

**不具合のときの流れ**: ① その機能を「止める」にして理由を書く → ② 直して確かめる(開発者には止めている機能も見えるので、本番の画面で確かめられる)→ ③ 「版に従う」に戻す(版が公開なら、また見える)。

**段 ① の作りから変えるところ(作る人への申し送り)**

- いまの「版を選んで、まとめて当てる」は、当てたときに全部の機能の行を書く(その時点の写し)。これだと、あとで版を付け替えた・足した機能が、版の公開についてこない。**版の公開の状態を持ち、行は上書きだけを持つ**形に変える。
- データの案(決めるのは作る人): 版の公開(版ごとに公開 / 非公開・だれが・いつ)、機能ごとの付け替えた版(空ならコードの値)、上書き(版に従う / 止める / 先に出す)・理由。いまの表 `feature_settings` に列を足すか、版の表を足す。履歴は、ほかの表と同じ変更の記録のしくみでよい。
- 行のない機能(`'*'`)の扱いは、「その機能の版が公開なら見える」に置き換わる(新しく足した機能も、版が非公開なら出ない)。

## 4. 版の定義(目安)

版の**ねらい**だけを書く。どの機能がどの版に入るかは、5 章の表だけが正(協議で 〇 を動かすのは、5 章の表だけ。動かしたら、管理の画面の版も付け替える)。

| 版 | ねらい |
|---|---|
| **MVP** | 企画が作れて、制作に渡せる |
| **v1** | チームで運用が回る |
| **v2** | AI で速く作る |
| **v3** | 結果を次に生かす |
| **v4** | 残りのすべて |

## 5. 機能の分類と公開の順番

**開発規模**は、その機能を「切り替えられるようにする」手間(入口を探して判定を入れ、隠したときに画面が崩れないようにする)。

- **小**: 入口が 1〜2 か所で、ほかの機能と絡まない(ボタンやメニューの項目を隠すだけ)
- **中**: 入口が数か所ある、または隠すと画面の並びが変わる・前提の確かめが要る
- **大**: 面・見せ方・ペインごと隠す、またはほかの機能の表示や確かめに絡む(隠したときに、ほかの画面も直す)

版の「常時」は、切り替えない土台(非公開にできない)。

表の見方: 大(A〜L)ごとに 1 つの表。行は中・小、〇 = その機能を作る(公開する)版。「常時」は切り替えない土台、「開発者」はどの版でも開発者だけに見せる(MVP の列に書く)。ID は、作るときに入口で使う名前(`isOn('ID')`)。
