# 業務の流れと前提運用

CCP が前提にしている業務の流れを、段階ごとに書いたもの。まず 0 章で、CCP が**何を解決するために**あるかを示す。**どこから入り、何をして、次にどこへ移るか**(画面の導線)と、**CCP が前提にしている運用**を、同じ表に並べた。次の 3 つに使う。

- **使う人に、前提の流れを先に伝える。** 使ってみてもらい、合わないところを確かめて直す(2026-10-19、利用者と決めた)。
- **今の運用を照らし合わせる。** 0 章の課題が今あるか、段階ごとの今の運用と前提に差があるかを聞く(進め方は 7 章、記入用のシートは [FLOWS_SHEET.md](FLOWS_SHEET.md))。差は、運用を CCP に合わせれば良くなるところか、CCP を直すところのどちらか。あわせて、要らない機能を見つける(3〜6 章)。
- **画面を整理するときに、流れに沿った導線を壊さない。** 整理の決まりと、これまでの整理の記録(気になる点 F1〜F14・変える候補 C-1〜C-12)は、[PRINCIPLES.md](PRINCIPLES.md) の付録に移した。

- 最終更新: 2026-10-20(0 章「解決する課題と、価値」を足した。同日、FLOWS.md と PROCESS.md を 1 つにまとめた。入り口・移り方は [FEATURES.md](FEATURES.md) と `src/` で確かめた。画面では確かめていない)
- この文書は、利用先に渡す資料にもなるので、社内のシステムの名前・本番の環境の名前は書かない。
- 承認のしくみの設計は [APPROVAL.md](APPROVAL.md)、制作の依頼の設計は [PRODUCTION.md](PRODUCTION.md)、デザインの方針は [PRINCIPLES.md](PRINCIPLES.md)、ファイルの場所は [SOURCE_MAP.md](SOURCE_MAP.md)。
- 機能の番号(F01 など)は、[FEATURE_REASONS.md](FEATURE_REASONS.md)(機能の理由の台帳)の番号。業務の作業・確認は [USER_STORIES.md](USER_STORIES.md)。

### 印

| 印 | 意味 |
|---|---|
| K1〜K9 | 解決する課題の番号(0 章) |
| A1・B4 など | 照らし合わせる業務の番号(A = 計画・起案、B = レビュー・承認、C = 制作、D = 変更・例外、E = 結果、G = チーム・国) |
| P1〜P13 | 前提の決まり(承認・制作の進め方の約束)の番号 |
| 差なし / 差あり / 業務はない | 照らし合わせの結果。**差なし** = 今も前提どおり、**差あり** = 今の運用が違う、**業務はない** = 今その業務をしていない(機能が要らないかもしれない) |
| CCP に合わせる / CCP を直す / 保留 | 差の扱い。**CCP に合わせる** = 運用を前提に寄せる(それで良くなる)、**CCP を直す** = 前提のほうが合っていない |
| 時間 / 質 / 事故 / 記録 / 新規 | 差があって、運用を CCP に合わせたときに良くなることの種類。**時間** = 手間が減る、**質** = 判断がそろう・根拠が見える、**事故** = 配信の間違いを前に防ぐ、**記録** = だれが・いつ・なぜが残る、**新規** = 今はできていないことができる |


## 0. 解決する課題と、価値

CCP が解決しようとしている課題と、それを**どの段階のどの業務で**解くか。課題は開発のときに挙げたもので、**利用先にはまだ確かめていない**。聞き取りで、まず課題が今あるかを聞く(7 章)。課題が「ない」なら、それを解く機能は、5 章の要検討の候補になる。

| # | 課題 | どの段階で | CCP での解決 | 業務 | 良くなること |
|---|---|---|---|---|---|
| K1 | 企画の素案づくりに時間がかかる | 2.2 起案する | 「すべてAIで下書き」で、テーマから制作指示まで一度に下書きする。週の枠(配信名・種類)を人が決め、まとめて AI で中身を作る | A2・A3・A6 | 時間 |
| K2 | 商品・メイン画像の選定が、人によって違う(属人的) | 2.2 起案する | 在庫・売上・評価・季節・天候・方針を踏まえた AI の選定と、その理由。商品情報のペインで、売上・在庫の推移と方針をその場で見る | A5・A7 | 質・事故 |
| K3 | メールの構成を、毎回作り直す | 2.2 起案する | テンプレート(構成の型)を選ぶ。チームで作って共有する | A4 | 時間・質 |
| K4 | 国ごとに、商品・言語・進め方が違う | 2.1 計画する・2.10.2 チーム・国・人 | 国を選ぶと、商品・画像・文言の言語がその国に合う。同じ画面で国を切り替えて見る | A6・G1 | 時間 |
| K5 | 週の計画のレビューが、資料づくりと確認で重い | 2.3 レビューする | 週の表示で 1 週間をまとめて見る。「確定の前に直すこと」が偏り・漏れを数える。指摘(コメント)も同じ画面で残す | B1・B2・B3 | 時間・事故 |
| K6 | 承認や、決まったあとの変更の記録が、メール・チャットに散らばる | 2.4 承認する・週を確定する | 配信ごとに承認を依頼し、承認・差し戻しと履歴が残る。確定したあとの変更には理由が要る | B4・B5 | 記録 |
| K7 | 制作への依頼とやり取りが散らばり、制作が商品情報を探し回る | 2.5 制作に依頼する・2.6 制作する | 制作のページ(承認された写し・項目ごとのコピー・配信ごとのやり取り) | C1・C2・C3 | 時間・記録 |
| K8 | 配信のあとで、在庫切れや方針の変更に気づく | 2.10.1 アラート | 配信日の在庫の見込みと、方針・日程の変更をアラートで知らせ、差し替えの案を出す | D1・D2 | 事故 |
| K9 | 振り返りが、次の企画に生きない | 2.9 結果を振り返る | 「次に生かすメモ」と週の振り返りを、次の配信カードと AI の案に渡す | E3 | 質・新規 |

- K1〜K5・K8・K9 は [FEATURES.md](FEATURES.md) の「解決する課題と、価値」から。K6・K7 は、承認と制作の依頼を作るときに挙げたもの。FEATURES の「AI の案が、気に入らない」は、今の運用の課題ではなく CCP を使うときの課題なので、ここには入れていない。

**価値**(課題を解いた先にあるもの)

- **人が決め、AI は提案する。** 素案と選定の理由を AI が出し、人はそれを見て判断する(K1・K2)。AI の案は、採用するまで反映しない。
- **配信の事故を、配信の前に防ぐ。** 偏り・漏れ・在庫切れ・方針の変更に、送る前に気づく(K5・K8)。
- **だれが・いつ・なぜ決めたかが、配信ごとに残る。** 承認・変更・制作とのやり取りが散らばらない(K6・K7)。
- **結果が、次の計画に返る。** 振り返りが、次の配信カードと AI の案に届く(K9)。

## 1. 流れの全体

| # | 段階 | 何を決めるか | 主に動く人 | 面 |
|---|---|---|---|---|
| 1 | 計画する | いつ・どのチャネルで・何本配信するか(週の枠) | 企画(マーケの担当) | 計画(Plan) |
| 2 | 起案する | 何を配信するか(テーマ・メイン画像・ヘッドライン・コピー・商品・制作指示) | 企画 | 計画の配信カード |
| 3 | レビューする | 週の配信の偏り・漏れ・方針との整合 | 企画・レビューする部署・MD | 計画の週の表示 |
| 4 | 承認する・週を確定する | 配信の中身でよいか | 承認者(承認グループのだれか) | 計画の配信カードの右端・週の帯 |
| 5 | 制作に依頼する | どう見せるかを、制作に頼む(制作指示・担当・締め切り) | 企画 | 制作(Production)の面・制作のページ |
| 6 | 制作する | 見せ方(メール・アプリの仕上がり) | 制作の担当 | 制作のページ |
| 7 | 仕上がりを確かめる | できたものでよいか(「これで OK」/「直してほしい」) | 企画 | 制作のページ |
| 8 | 配信する | 配信のしくみに入れて送る | 企画・制作 | (配信のしくみ。CCP の外) |
| 9 | 結果を振り返る | 送ったあとの数字と学び。次の計画に返す | 企画 | 結果(Results)の面 |

- 1〜4 は「**何を配信するか**」の話で、企画とその関係者(レビュー・承認する部署)のやり取り。
- 5〜7 は「**どう見せるか**」の話で、企画と制作のやり取り。
- 9 の学びは、次の週の 1・2 に返る(週のサイクル)。
- Plan・Production・Results は、**同じカレンダー(配信日)**の表・中・裏。同じ配信が、どの面でも同じ日・同じ位置に出る。
- 流れの外で起きること(在庫切れ・方針や日程の変更・取りやめ)は、**アラート**で知らせ、その配信の段階に戻して直す(2.10)。

### 1.2 段階の名前は「いま、だれの番か」で言う

状態だけを言う名前(「承認済み」「引き継ぎ済み」)は、見る人によって意味がぶれる。次に動く人を添えて言う。

| 面 | 状態 | 次に動く人 |
|---|---|---|
| 計画 | 未起案 / 企画を作っている | 企画 |
| 計画 | 承認待ち | 承認者 |
| 計画 | 承認済み(週が確定すると鍵) | — (制作へ) |
| 制作 | 制作に依頼する前 | 企画 |
| 制作 | 依頼済み(受け取り待ち) | 制作 |
| 制作 | 制作している | 制作 |
| 制作 | 制作が終わった | 企画(仕上がりの確認) |
| 制作 | 制作を通さず、配信のしくみに送った | 企画 |

## 2. 段階ごとの流れ

段階ごとに、上の表が**画面の導線と前提の決まり**、下の表が**照らし合わせる業務**(CCP の前提運用と、今の運用に差があったときに良くなること)。聞き取りでは、「聞くこと」を聞きながら、下の表の業務ごとに差を付ける(7 章)。

### 2.1 計画する

| | |
|---|---|
| だれが | 企画(国ごとのチーム) |
| 入り口 | 計画の面の月のカレンダー / 週の表示 / 一覧。ヘッダーの「＋ 新規作成 ▾」(1 本作る・「まとめて作る」・「この週の枠を作る」)、カレンダーの日からの新規作成 |
| すること | 日・チャネル・種類の割り振りを見る。国はヘッダーで、自分の分は作業の段の絞り込み(担当の「自分」など)で絞る。週の枠を作り、配信名と種類を入れる。週の見方「時刻」で同じ時刻の偏りを見て、配信をつかんで別の日・時刻へ動かす(15 分きざみ)。「商品別」で、商品ごとの掲載の回数と外部広告を見る。配信日が近いのに未着手の配信と、アラートのある配信に印 |
| 次への移り方 | 配信を押す → 配信カード(上に重ねる)。月の各週の先頭の「週 ›」で、その週の週表示へ |
| 聞くこと | 配信の予定・進み具合を、どこで持っているか(表計算・予定表・ほか)。国・チャネル・部署で分かれているか |

| # | 業務 | CCP の前提運用 | 差があったときに良くなること | 機能 |
|---|---|---|---|---|
| A1 | 月・週の配信の予定を立てる | 計画の面のカレンダー 1 つに、国・チャネル・種類・担当で絞って見る。状態の色で進み具合が分かる | 時間・記録 | F01〜F04, F68, F97, F101, F105 |

|---|---|
| だれが | 企画 |

| すること | 左の「すべてAIで下書き」、または中ペインの「コンテンツ生成」で ①テーマ → ②テンプレート → ③ヒーロー → ④セクション → ⑤リンク先 → ⑥制作指示。AI チャットで、開いている工程の案を直す。上に「これまでの学び」、プレビュー、右に商品情報(参照専用)。商品の差し替えは商品のフロートから |

| A3 | テーマを決める | AI のテーマの 3 案と理由から選ぶ。ほかの配信と重ならない案にする | 時間・質 | F18〜F20 |

### 2.3 レビューする

| | |
|---|---|
| だれが | 企画・レビューする部署・MD |
| 入り口 | 計画の面の週の表示。週の帯の「確定の前に直すこと」(⚠ と数)。週の見方「商品 / 進み具合 / 時刻」。帯の下の「前週の振り返り」 |

| B2 | 商品の偏り・漏れを確かめる | 「確定の前に直すこと」が、同じ商品の回数・主力の漏れ・テーマや画像の連続・未対応のコメントを数え、何をするかを出す | 時間・事故 | F71, F100 |
| B3 | 意見を出し、直してもらう | 配信ごと・商品ごとの指摘を「やり取り」にスレッドで残し、「解決にする」 | 記録 | F72 |

### 2.4 承認する・週を確定する

| | |
|---|---|
| だれが | 企画(依頼する)・承認者 |
| 入り口 | 配信カードの右端のプロセスのペイン(状態と承認)。週の帯の「まとめて依頼」「自分宛てを承認」「週を確定」。承認者は、ヘッダーの「依頼」(自分宛ての承認の依頼) |
| すること | 承認を依頼する。承認者が「承認」、または理由を付けて「差し戻す」(変更があるときは、先に「保存」する)。週の配信がそろったら「週を確定」。履歴は「この画面 ▾」→ この週の承認の履歴 |
| 次への移り方 | 承認されると、プロセスのペインに「次: 制作に依頼する」が出る(2.5)。配信カードは開いたまま |

## 5. 機能の要否の棚卸し

機能を 3 つに分ける。**要検討**は、使ってみて要らなければ外す・まとめる候補。

| 分け | 意味 |
|---|---|
| 芯 | ないと、1 章の流れが回らない |
| 良くする | なくても回るが、2 章の「差があったときに良くなること」を生む |
| 要検討 | 別の機能と重なっている、または前提が合わないかもしれない |

### 5.1 芯

- 計画のカレンダーと配信カード(F01, F07, F08)、状態の色(F02)
- 配信の中身: テーマ・テンプレート・メイン画像・文言・セクション・商品・リンク先・制作指示(F18, F21, F31, F33, F37, F40, F65, F61)
- 承認の依頼・承認・差し戻しと履歴(F73)
- 制作の面と制作のページ(F111)
- 国ごとの商品・画像・言語(F32, F34)

### 5.2 良くする

- AI の下書き・選定と理由(F14, F30, F39, F12)、AI チャット(F48)
- 商品情報のペイン(F45, F47)、プレビュー(F52〜F58)
- 週の表示と「確定の前に直すこと」(F68, F71)、コメント(F72)
- アラート(F88〜F94)
- 結果の面と、次に生かすメモ(F77〜F85, F103)
- リンクをコピー(F106)

### 5.3 要検討

| # | 機能 | なぜ要らないかもしれないか | 確かめること | 要らなければ |
|---|---|---|---|---|
| R1 | 週の確定(F69, F70)と、配信ごとの承認(F73)と、配信の状態(F02) | 「承認済み」と「確定」の 2 段がある。配信ごとに承認するなら、週の確定は重いかもしれない | 週で区切って締める場面が、今の運用にあるか | 週の確定をやめ、配信ごとの承認だけにする |
| R2 | 制作への「引き継ぎ」のタブ(F66: 担当・締め切り・引き継ぎ済み) | 制作のページの「制作に依頼する」(F111)と役目が重なる。担当・締め切りを 2 か所で持つ | 制作の依頼を使い始めたあと、引き継ぎのタブを使う人がいるか | 引き継ぎのタブを外し、制作の依頼にまとめる |
| R3 | 下書きの入口が 3 つ(すべてAIで下書き F14・開いたとき自動で下書き F15・まとめて AI で作る F76) | 入口が多いと、どれを使うか迷う | どの入口が使われているか | 使われない入口を外す |
| R4 | 週の資料の PDF(F74) | 画面の中でレビューするなら、資料は要らない | 画面を開けない人(役員・他部署)に見せる場面があるか | 外す |
| R5 | 詳しい結果の PDF(F86) | 結果の共有を、リンク(F106)で済ませられるかもしれない | 結果を社外・画面を開けない人に渡すか | 外す |
| R6 | 制作の工程の「受け取った」(② の段) | 依頼 → 制作 → 確認の間に 1 段増える | 制作が受け取ったかどうかを、企画が気にするか | 依頼したら「制作している」にする |
| R7 | 制作のページの HTML のエディタ | 制作が別の道具で作るなら、使われない | 制作が、どこで仕上げているか | HTML の書き出しだけにする |
| R8 | 制作を通さずに、配信のしくみに送る | 制作を通さない配信がないなら、要らない | 制作を通さない配信(アプリの通知だけ、など)があるか | 外す |
| R9 | 利用者が作るテンプレート(F25, F26) | 標準の 10 種で足りるなら、管理の手間だけが残る | 自分で作ったテンプレートが使われているか | 作る機能を管理者だけにする |
| R10 | テーマの種類の AI での分け(F83, F110) | 企画のときに種類を選ぶなら、後から分けなくてよい | 種類を、企画のときに選んでいるか | AI での分けを外す |
| R11 | 結果の「まとめて見る」(F80)と「比べる」(F82) | どちらも過去の配信と比べるもので、重なる | どちらを使っているか | 1 つにまとめる |
| R12 | 配信の対象(性別・年代。F109) | 対象を配信のしくみ側で決めているなら、CCP では要らない | 対象を、企画のときに決めているか | 外す(AI の前提からも外す) |
| R13 | 自分で依頼した配信を、自分で承認する | 承認の意味が薄れる | 承認を、別の人が行う決まりがあるか | 自分では承認できないようにする |

- 要検討の機能も、使ってみるまでは外さない。2〜4 週使ったあと、使った人に聞き、6 章の物差しと合わせて決める。
- 決めたことは、この表の「要らなければ」の列を「外した(日付)」「残す(理由)」に書き換える。

## 7. 照らし合わせの進め方

1. 0 章の課題(K1〜K9)を見せ、それぞれ今あるか(ある / ない / 一部)を聞く。
2. 段階ごとに、2 章の表(画面の導線・前提の決まり・CCP の前提運用)を見せる(読み上げる)。
3. 「聞くこと」を聞き、業務ごとに今の運用を書く(だれが・何で・どのくらい)。
4. 業務ごとに「差なし / 差あり / 業務はない」を付ける。差ありなら「CCP に合わせる / CCP を直す / 保留」を、その場で利用先と決める(決められなければ保留)。前提の決まり(P1〜P13)も、1 つずつ読み上げて同じように付ける。
5. 5 章の要検討と、6 章の今の値も、同じ場で聞く。
6. 全体として、CCP を使い始めたら、やめる資料・やり取りはどれかを聞く(4 章の「二重になる」)。
7. 終わったら、結果を 3.2 に書き、0 章の課題・3.1 の ● と 5 章を見直す。

聞き取りの記録には、記入用のシート [FLOWS_SHEET.md](FLOWS_SHEET.md) を使う(聞き取り先ごとに写して書く。紙に刷るなら横向き)。課題・業務・前提の決まり・要否・今の値の行が、この文書と同じ番号で並ぶ。`python scripts/flows-sheet.py` がこの文書の 0 章・2 章・5.3・6 章から作るので、それらの表を変えたら流し直す。

### 7.1 使ってみて確かめたいこと(前提の流れ)

- 承認の段階(起案 → 承認待ち → 承認済み)と、週の確定の 2 つで、足りるか・多すぎないか(5 章の R1)。
- 承認グループと「全員 / 1 人」の決まりで、実際の承認の進め方に合うか。
- 制作に依頼するのは承認のあと、という順で困らないか(承認の前に制作に見せたい場面がどのくらいあるか)。
- 制作の人が、制作のページだけを見て作れるか(足りない情報・コピーしにくいものは何か)。
- 依頼のあとに直した内容を、配信カード(企画)にも戻したいことがあるか(いまは戻さない)。どこまで直してよいか(承認のやり直しが要る変更はあるか)。
- 写しを固める時点(依頼したとき)でよいか。依頼のあとに企画が変わったとき、どう知らせてほしいか。
- 「受け取った」「制作が終わった」のほかに、制作の人が押したい返事はあるか(「受け取った」自体が要るかは 5 章の R6)。
- HTML のソースは、どこで・どう使うか(配信のしくみに入れるか、制作の出発点にするか。5 章の R7)。
