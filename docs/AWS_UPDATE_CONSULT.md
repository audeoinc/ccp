# 相談: CCP の更新方法を「ZIP で総入れ替え」から「ベンダーブランチでマージ」に変えるか

この文書は、AWS の環境で作業している Claude に読んでもらうものです。開発側の Claude が、利用者と相談してまとめました。

**お願い:**
- いまの環境を調べて、最後の「聞きたいこと」に答えてください。
- **この文書を読んだだけで、ブランチの作成やマージを始めないでください。** Git の履歴・設定・サーバーの状態を変えず、読むだけで調べてください。
- まだ決定ではなく案です。環境に合わない所があれば、遠慮なく指摘してください。

## 1. 背景

- CCP は開発側で作り、版ごとに ZIP(`ccp-aws-<版>.zip`)で届きます。
- 届いた ZIP を利用先の Git に入れ(`CCP AWS 版 <版>` でコミット)、サーバーは `scripts/workbench.sh update` で取得します(`docs/AWS.md` の 8 章)。
- 開発側が案内している入れ方は、`.git` 以外をすべて消して、ZIP の中身を置く形です(手順の文書は、リポジトリの `docs/UPDATE.md`。ZIP には入っていません)。
- `CLAUDE.md` には「このリポジトリの中で、コードを直さない。次の版で上書きされる」と書いてあります。

## 2. 課題

カテゴリの分類、商品コード、商品ページの URL の構成などは、クライアントごとに変わります。こうした部分は相手の環境に合わせて調整しつつ、画面や機能は開発側で作ったものを取り込み続けたい、というのが利用者の希望です。

いまの総入れ替えには、次の問題があります。

| 問題 | 内容 |
|---|---|
| 直しが消える | 向こうでコードを直しても、次の版で消える |
| 差分が見えない | 向こうで何を変えたかを確認する道がない |
| 急ぎの直しができない | 止まって困るときでも、直せば次の版で失われる |

## 3. 調整の線引き(案)

コードを直せるようになっても、調整はできるだけコードの外に置きます。マージのたびにぶつかるのを避けるためです。

| 層 | 例 | 直す場所 | 更新の影響 |
|---|---|---|---|
| データの出力 | カテゴリの分類・商品コード・`page_url`・`gender` の値 | BigQuery のビュー(SQL) | 受けない |
| 設定 | 店の URL の形・表の場所・AI・国ごとの設定 | CCP の画面(DB) | 受けない |
| コード | 画面・機能・取り込みの仕組み | 原則として開発側。急ぐときだけ向こうで直し、内容を開発側へ伝える | マージの対象 |

開発側の案では、次はコードの外に任せます。
- 商品コードの一部から URL を作る処理: ビューの中で `page_url` を作る
- カテゴリの違い: ビューで整える。CCP 側は、カテゴリの選択肢の固定をやめる方向(開発側の作業で、まだ決定ではない)

## 4. マージの方法(案)

利用先の Git に、ブランチを 2 本持ちます。

```
vendor : ZIP の中身だけを入れる(手で直さない)  ── v1 ── v2 ── v3
                                                    \     \     \
main   : 実際に動かす(向こうの調整が載る)  ── 調整 ─ merge ─ merge ─ merge
```

### 4.1 最初の 1 回

いま `main` で動いている版を、`vendor` の出発点にします。ZIP の版のコミットのあとに手で直したコードがあれば、それより前の、ZIP を入れたままのコミットから作ります。

```bash
git switch -c vendor <ZIP を入れたままのコミット>
git push -u origin vendor
```

### 4.2 版が届くたび

```bash
VER=<版>
git switch vendor
git pull

# .git 以外を消して、ZIP の中身を置く(前の版にあって、新しい版にないファイルを残さないため)
find . -mindepth 1 -maxdepth 1 ! -name .git -exec rm -rf {} +
TMP=$(mktemp -d)
unzip -q ~/ccp-aws-$VER.zip -d "$TMP"
cp -a "$TMP/ccp-aws-$VER/." .
rm -rf "$TMP"

git add -A
git commit -m "CCP AWS 版 $VER"
git tag "aws-$VER"
git push origin vendor --tags

git switch main
git pull
git merge vendor          # ぶつかれば、ここで解消する
git push origin main
```

サーバーは、これまでどおり `main` を `scripts/workbench.sh update` で取得します。

### 4.3 向こうで変えた所を見る

```bash
git diff vendor main --stat
git diff vendor main
```

### 4.4 ぶつかったとき

- 開発側と向こうが同じ行を変えたときだけ、ぶつかります。
- 解消するときは、まず開発側の変更で目的が足りているかを確かめます。足りていれば、向こうの直しをやめて、開発側に合わせます(差分を減らすため)。

### 4.5 開発側へ戻す

向こうでコードを直したら、内容を開発側へ伝えます。開発側が同じ直しを入れれば、次の版のマージのあと、`git diff vendor main` からその差分が消えます。

## 5. 想定している注意点

- 差分が増えるほど、マージのたびにぶつかりやすくなります。
- 秘密(`server/workbench.env`・鍵のファイル)や写真のフォルダは、Git の外のままです。
- 4.2 の `find` は、Git の外のファイル(`server/workbench.env`・写真など)も消します。**サーバーの上の作業コピーでは実行せず、別の場所の作業コピーで行う**前提です。
- 開発用の画面の SQL の版(`server/devwork/`)は、Git の外です。残し方を別に考える必要があります。
