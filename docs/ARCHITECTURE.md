# 構成と設計の約束事

## 2. AI の仕組み

### 2.1 呼び出し(`src/aiSelect.ts`)

1. `askAgent(prompt, payload)` が、指示文 + 入力の JSON を、AI の依頼として送る(`AiRequestsService` → `src/gcp/ai.ts` → サーバーの `/api/ask`)。
2. サーバーが Gemini に問い合わせ、返答のテキストを返す(`server/ccp/ai.py`)。
3. 画面が、返答から JSON を取り出す。
- 返答の JSON が壊れていたときは、最大 3 回まで依頼し直す。末尾のカンマは自動で直す。
- AI は、指示に反して説明文を付けることがあるので、**最初の `{` から最後の `}` まで**を取り出して読む(`extractJson`)。
- 依頼によって、`askAgent` が入力と指示文に足すもの: チャットの履歴(`withChat` の間だけ)、これまでの学び(`setActiveLearnings`。案を作る依頼だけ)、**商品の MD 方針**(`setActivePolicies`。商品の候補の `md` に段階・方針・販促の予定と期間を付け、そのときだけ `MD_NOTE` で使い方を伝える。バックログ M2)。

### 2.2 指示文(プロンプト)

- `aiSelect.ts`(セクション、商品、メイン画像)と `aiDraft.ts`(テーマ、コピー、制作指示、テンプレートの選択)に、日本語で書いてある。
- **出力の言語**: 画面が English のときは、`localizePrompt` が、指示文の「日本語で書く」を「英語で書く」に置き換え、文字数の上限を英語の長さに直す。コピーとヘッドラインの言語は、別(`language`: auto / ja / en。auto は、配信カードの国に従う)。
- 商品・メイン画像は、AI に渡す前に、**配信カードの国に合う市場(JP / US)のものだけ**に絞る(`CardDetail.tsx` の `poolProducts` / `poolHeroes`)。

### 2.3 チャット(`src/ChatPanel.tsx`、`aiSelect.ts` の `withChat`)

- 開いているタブの案づくりに、ユーザーの指示と、これまでの対話(最大 12 発言)を加えて、同じ「案を作る」処理を呼び直す。
- AI は、発言が質問・相談のときは `mode: "answer"` で答えだけを返し(案は変えない: `ChatAnswer` を投げて、呼び出し側が無視する)、作り直しの依頼のときは `mode: "update"` で案と `reply` を返す。
- 会話は、画面を開いている間だけ保持する(保存は未実装。[BACKLOG.md](BACKLOG.md))。

### 2.4 すべてAIで下書き(`src/autoDraft.ts`)

テーマ → テンプレート + メイン画像 → ヘッドライン・コピー → 各セクション(順に)→ 制作指示。結果は画面に反映するだけで、保存はしない。

週の枠からまとめて AI で中身を作る(W14。`src/bulkDraft.ts`・`src/useWeekFrames.ts`)も、同じ `runAutoDraft` を使う(作り方を、配信カードとずらさないため)。保存は、配信カードの保存(`buildContent`・`syncItems`)と同じ形にそろえる。配信カードの保存の形を変えたら、`bulkDraft.ts` の `contentFields`・`saveProducts`(週の枠に書き込む `applyResult` と、作業画面で新しく保存する `createDraft` が使う)も直す。まとめて作る作業画面(`src/useBulkWorkspace.ts`・`src/BulkWorkspace.tsx`)は、中身のない枠を保存せず、中身ができた配信から「未起案」で新規作成する。

## 3. 画面の構成

`CardDetail.tsx`(ダイアログ)が、5 つのペインを持つ(幅は、境界のドラッグで変更。保存される。キーは `cardDetail.paneWidths.v6`)。左〜商品情報は配信を「作る」、右端のプロセスは配信を「進める」(2026-10-17、利用者と決めた)。

| ペイン | 内容 |
|---|---|
| 左 | 配信情報、テーマ・ヘッドライン・コピー・制作指示(AI の理由・切り口つき)、「すべてAIで下書き」 |
| 中 | `ContentPane.tsx`: コンテンツ生成の工程(テーマ / テンプレート / ヒーロー / セクション / リンク先 / 制作指示。アプリは 通知 / メッセージ / リンク先 / 時刻・相手)と、下半分に `ChatPanel`(AI チャット) |
| プレビュー | `Preview.tsx`: メール・プッシュのプレビュー。ドラッグ&ドロップで商品を並べ替え |
| 商品情報(既定は開く) | `ProductInfoPane.tsx`: 商品の一覧(操作する部品は置かない)。行を押すと、商品のフロート `ProductFloat.tsx`(中身は `ProductDetail.tsx` の売上・在庫のグラフ、MD 方針と、「ほかの候補から選ぶ」。右上の × で閉じる)。プレビューとセットで見るので、プレビューのすぐ右 |
| 右端: プロセス(既定は開く。`cardDetail.processOpen.v1`) | `ProcessPane.tsx`: 上に状態と承認(`ApprovalBar`。いつも見える)、下にタブ: 引き継ぎ(担当・締め切り・渡す制作指示を読むだけで。直すのは中の ⑥)/ やり取り(以前の質問とレビューのコメントを 1 つに。`CommentsPanel`。宛先・対象・返信・解決・AI でタスクの案)/ タスク。閉じると、帯に状態を縦書き(`ProcessRail`。状態・承認の残り・未解決のやり取りの数) |

- **右端の商品情報の一覧には、操作する部品を置かない。差し替えは、商品のフロート(または、アラートへの対応のパネル `CardAlertAction`)から行う。並べ替え・外す・理由の編集は、中ペインだけ**(2026-10-20 に改めた。X47)。
  - 商品のフロート(`ProductFloat`)は 1 つで、中の「選定済み」の行からも、右の商品情報の行からも、同じものを開く(数字を見て違和感があれば、人の感覚で商品を変えたくなる。その操作は、中からも右からも起こるため)。行の中のボタン・入力欄・理由の文(`data-no-float`)を押したときは開かない。
  - 「ほかの候補から選ぶ」に出すのは、中ペインの「残りの候補」と同じもの(AI が案出しで作った候補、同じ順番)だけ。別の決め方の候補は作らない。選ぶと、配信カードの中で入れ替え(外した商品は残りの候補に戻る。どちらの行も行 ID のまま状態だけが変わる)、保存で確定する。理由は任意で、保存のときに配信のメモ(kind change)に残す(X30 のアラートへの対応と同じ記録)。
  - 「問題なし / 注意」のような判断の表示は作らない(AI は問題のある商品を選ばない。あとから起きる問題は、アラートと X30 が受け持つ)。中の「選定済み」の行にも、商品情報と同じ印(「残少」・アラートの札。`ProductMarks.tsx`)を出す。
- 選定のロジックは、`useSelection.ts` に集約している。
- 商品が載るメールの構成(セクション)は、テンプレートで決まる(後述)。

## 4. データの読み書き(`CardDetail.tsx`)

- 配信カード: 表 `delivery_cards`。AI の理由・切り口(`theme_reason` など)、セクションの見出し(`section_titles`)・コピー(`section_copies`、JSON)も、ここに保存する。
- 掲載商品: 表 `delivery_products`(1 行 = 1 商品)。`state`(`selected` 選定 / `candidate` 候補)、`section`(セクション番号)、`sort_order`、`reason`、`source`(AI / 手動)を持つ。保存時は、読み込み時点との差分で、作成・更新・削除する。
- 候補(`state` = 候補)は、保存する。AI の案(テーマ・コピー・制作指示の案、セクションの見出し・コピーの候補)は、**保存しない**(画面を開いている間だけ)。
- 週の枠からまとめて中身を作る(W14)ときは、人が「中身を作る」を押すことを、AI の第 1 候補の採用とみなして保存し、「AI 下書き・未確認」の印(`ai_unchecked_at`)を付ける。印は、人が配信カードで保存するか、「確認した」を押すと外れる(誰も確かめていない中身を、印で見分けるため)。
- まとめて作る作業画面(`BulkWorkspace`)は、AI の案を保存せずに画面だけに持ち、人が 1 本ずつ「保存」したものだけを、ふつうの下書き(未起案)で保存する(未確認の印は付けない。保存しなかった案は破棄)。週の表示で枠(破線)として出すのは、「この週の枠を作る」で作った配信(`frame_at`)だけ。
- 選択肢(ステータス、チャネル、カテゴリなど)は、文字の値(例: `email` / `app`)で持つ。表示名(`○○_name`)は、`labels.ts` が、値から補う。状態の前後は `statusRank` で比べる(文字のまま `<` で比べない)。
- **承認の流れ(2026-10-14 決定。2026-10-17 の U1〜U6 で、下の「ユーザーと承認」の形に変えた。データの値と `statusRank` の順はそのまま)**: データの値は、配信が 未起案(not_started)→ 検討中(reviewing)→ 承認済み(approved)→ 確定(confirmed)、週が 下書き(draft)→ レビュー中(review)→ 確定(confirmed)。**画面では**、配信を 未起案 / 承認待ち / 承認済み(+ 確定した週は鍵マーク)、週を 確定前 / 確定 と見せる(`src/status.ts` の `statusView`・`statusLabel`、`LockMark`)。
  - 承認は、配信 1 本ずつ(配信カードの「保存して承認」)と、週まとめて(週の帯の「まとめて承認」= 検討中をすべて承認済みに)の両方。誰でも押せる。
  - 差し戻しは、理由が必須。配信は検討中になり、理由はレビューのコメント(未対応)にも残す。
  - 承認済み・確定の配信の内容を変えて保存すると、検討中に戻る(再承認が必要)。変わったかは、開いた時点の内容と比べる(保存済みの行と比べると、表し方の違いだけで変わったことになるため)。確定した週の配信は、理由つきの確定後の変更(W3)の流れになる。
  - 確定は、週単位(「週を確定」)。「承認済み」(内容が OK)と「確定」(制作に回してよい)は、分けて残す。
  - 「誰が」は、ログインで人を見分けないので、画面で入れた名前(`me.name`)。操作は、操作の履歴(`events`)に残す。通知はしない。
- **ユーザーと承認(2026-10-17 決定。設計は [APPROVAL.md](APPROVAL.md)。バックログ U1〜)**: 配信カードごとに承認を依頼し、承認グループ(だれか 1 人で済み)・人が承認する形に変えていく。決まりは全員 / 1 人、自分の依頼は承認できない、1 人でも差し戻したら止める、1 回の承認は 1 グループ分。通知はメールが飛ぶ前提で送る箱に積む。上の W9 の流れは、U4 ができるまで残す。
  - ユーザーマスタ(`users`。メールアドレスが本人を見分けるかぎ)と承認グループ(`approval_groups`・`approval_group_members`)は、⚙ →「ユーザーと承認グループ」(`PeopleManager.tsx`)。読み込みは `people.ts`(画面全体で 1 回。編集したら `reloadPeople`)。ログインが入るまでは、だれでも編集でき、変更は `events` に `user_change` / `group_change` で残す。
  - 「あなた」= ログインしている人(U9。2026-10-19)。右上の `MePicker`(アカウントの見た目。押すと「ユーザーを切り替える(デモ)」)で選んだ人を、ログインしている人とみなし、ほかの画面(承認のブロック・やり取り・ユーザーと承認グループ)では人を選ばせない。初回は `SignInDialog` で選ぶ。本物のログイン(U7)が入れば、切り替えが消えるだけ。ユーザーがいなければ、これまでどおり名前を入れる。記録は、これまでどおり名前の文字(`me.name`)で残す。
  - 承認の依頼・承認・差し戻し・取り下げは、サーバーの窓口 `/api/approvals`(`server/ccp/approvals.py`)だけで行う(配信カードの `ApprovalBar`、週の帯の `weekApprovals.ts`)。判定は `src/approvals.ts` と同じで、`server/tests/approval_cases.json` の例を両方で確かめる。通知は送る箱 `notifications` に積むだけ(送る仕組みは未実装)。ヘッダーの「依頼」は、依頼中の依頼から計算する(`useApprovalInbox`)。

## 5. テンプレート(`src/templates.ts`、`layoutTemplates.ts`)

- **標準の 10 種**は、コードに持つ。編集・削除できない。以前からの 6 種(free, standard4, collab, offer, cat2, cat3)と、新しい部品を使う 4 種(sale, spotlight, story, editorial)。
  - 以前からの 6 種は、**セクションの構成を変えない**。保存済みのカードは、商品をセクションの順に流し込み、見出し・コピーもセクションの番号で持つので、構成を変えると位置がずれる。見た目の設定(ヘッドラインの見せ方・ボタン)だけ変えてよい。
  - 新しい 4 種は、以前の選択肢の列(`emailtemplate`)に値がないので、`layoutkey` だけで指す。
- **セクションの部品**(`Section.kind`): grid(名前・価格つき。2 / 3 列)、photos(写真だけ。2 / 3 列)、wide(全幅で大きく 1 点ずつ)、mosaic(大 1 点 + 小 2 点で 1 組。枠は 3 の倍数。`flip` で大きい枠を右に)、story(写真と商品の説明を左右交互)、feature(特集)。どの部品にも、見出し(`categoryHeading`)を付けられ、コピーを外せる(`copy: false`。省略はコピーあり)。
- **ボタンの部品**(`ButtonBlock`): セクションとは別に、`buttonBlocks`(`at` = その前にあるセクションの数。0 はヒーローの直後)で持つ。商品の枠の位置の計算(`sectionsOf` など)は、セクションだけを見るので、ボタンを足しても、商品・見出し・コピーの位置はずれない。
  - ボタン(`ButtonSpec`)は、変わらない `id`、文言(`label`。空は既定の文言)、見た目(`style`: fill / outline)、リンク先の種類(`link`: campaign / category / top / custom)を持つ。**`id` は、配信カードでボタンごとの URL を持つときの鍵**にする(文言や位置を変えても、URL が外れないように)。
  - 以前の形(ヒーローの `heroButtons`、セクションの `buttons`)も読む。描画は `placedButtons` が、以前の形を、位置 0 / セクションの後のボタンの部品に直して、まとめて返す。管理画面で開くと、部品に置き換わり、保存すると以後は部品として持つ(標準のテンプレートは、以前の形のまま)。
- **ヒーローの見せ方**(テンプレート全体): `heroText`(band: 写真に帯で重ねる / overlay: 写真に大きく重ねる / below: 写真の下)、`heroLink`(画像のリンク先の種類)、`topBar`(お知らせ帯)。
- **リンク先**は、テンプレートには種類(既定値)だけを持つ。実際の URL と計測用のパラメーターは、配信カードに持たせる予定(未実装。[BACKLOG.md](BACKLOG.md))。
- 見取り図(`TemplateThumb.tsx`)は、実際のメールに近い縦横比で、縦長に描く。一覧では上の部分だけ(`maxHeight`)、管理画面では全体を表示する。
- **ユーザーが作ったテンプレート**は、テーブル `layout_templates` に保存する(名前、説明、ヒーローの種類、セクションの JSON)。アプリの起動時に読み込み、`setCustomTemplates` で登録する。
  - ヒーローの見せ方は、列がないので、セクションの JSON の先頭に `{"kind":"hero",...}` として入れる(`layoutTemplates.ts`)。ボタンの部品は、置く位置に `{"kind":"buttons","buttons":[...]}` として挟む。どちらも `slots` を持たないので、以前の版のアプリは読み飛ばす(ボタンが出ないだけで、商品の位置はずれない)。知らない部品(`slots` あり)は、グリッドとして読む。
  - 既定の値は書かない。ヒーローが既定で、ボタンの部品もないテンプレートは、以前と同じ形(セクションの配列だけ)になる。
- 配信カードは、`layoutkey`(標準は ID、作ったものは行の GUID)でテンプレートを指す。標準のテンプレートは、以前の選択肢の列(`emailtemplate`)にも書く(互換)。`layoutkey` が空なら、選択肢の値から決める。
- 登録にない ID(削除された、まだ読み込まれていない)は、Standard4 として扱う。
- 管理の画面は、ヘッダーの「テンプレート」ボタン、または、配信カードの「②テンプレート」タブから開く(`TemplateManager.tsx`)。

## 6. 日本語・英語(`src/i18n.ts`)

- **画面の文言は、その場に `t('日本語', 'English')` と書く**(コンポーネントの先頭で `const t = useT()`)。React の外では `tr('日本語', 'English')`。辞書ファイルは使わない。日本語だけの文言を、画面に書かない。
- モジュールの最上位に、日本語の文言を持つ定数を置かない(言語を切り替えても変わらなくなる)。関数にするか、getter(`get label() { return tr(...) }`)にする。
- 日付・数値は `locale()`、価格は `yen(price, market)`(US の商品はドル、JP の商品は円)。
- 選択肢のラベル(日本語)は、`optionLabel(label)` で、表示だけ英語にする(値は変えない)。辞書は `i18n.ts` の `OPTION_EN`。
- 商品・メイン画像は、`market` 列(JP / US)で区別する。空は JP とみなす(`market.ts`)。US の商品の画像は、同じイラストを使い回す(`images.ts`)。

## 7. 見た目の約束事

- **Fluent UI v9** のみ。MUI は使わない。スタイルは、`makeStyles` と `tokens`(`@fluentui/react-components`)で書く。色を、直接(`#fff` など)書かない(メール・プッシュのプレビュー内の、受信側の見た目を再現する部分だけ例外)。
- 文字の階層: ラベル(項目名)= 12px・中太・薄いグレー(`index.css` で、全入力欄に一括で効かせている)、値 = 12px・標準、見出し・カードのタイトル = 13px・中太、補足 = 12px・薄いグレー。
- テーマ(`theme.ts`): インディゴ寄りのブランド色。OS のライト / ダークに追従する。
- お知らせの帯(`MessageBar`)は、`layout="multiline"` にする(ボタンが文字に重なるため)。
- 複数行の入力は、`AutoTextarea`(内容に合わせて高さが伸びる)を使う。

## 9. 落とし穴(過去にはまったこと)

- CSS の `zoom` を使う箇所(`items.ts` の `scaled`、プレビューの倍率)では、**幅を `%` で補正しない**(現在のブラウザの仕様では、枠より広がる)。
- Fluent の `Switch` の色は、ヘッダーのような色付きの背景では、効きにくい(ヘッダーのトグルは自作)。
- Fluent の `Textarea` には最低の高さがある(`AutoTextarea` で解消している)。
- 列を変えたら、`server/schema.json` と画面の型(`src/models/`、一部の表は `src/data/`)を一緒に直す(`npm run verify` が食い違いを見つける)。
- ファイルの改行コードが、CRLF のものと LF のものが混在している。スクリプトで一括置換するときは、改行コードを保つ。
