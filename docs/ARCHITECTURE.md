## 2. AI の仕組み

### 2.1 呼び出し(`src/aiSelect.ts`)

1. `askAgent(prompt, payload)` が、指示文 + 入力の JSON を、AI の依頼として送る(`AiRequestsService` → `src/gcp/ai.ts` → サーバーの `/api/ask`)。
2. サーバーが Gemini に問い合わせ、返答のテキストを返す(`server/ccp/ai.py`)。
3. 画面が、返答から JSON を取り出す。
- 返答の JSON が壊れていたときは、最大 3 回まで依頼し直す。末尾のカンマは自動で直す。
- AI は、指示に反して説明文を付けることがあるので、**最初の `{` から最後の `}` まで**を取り出して読む(`extractJson`)。
- 案を作る依頼(suggest_ / select_)のたびに、`askAgent` が、開いている配信カードと、渡した学びの id を `ai_runs` に記録する(学びを渡さなかった依頼も。結果の面の「効果」で、学びあり / なしを比べるため。X56)。AI の案そのものは保存しない。
- 依頼によって、`askAgent` が入力と指示文に足すもの: チャットの履歴(`withChat` の間だけ)、これまでの学び(`setActiveLearnings`。案を作る依頼だけ。渡すのは配信カードの「装備中の学び」= 自動で選んだもの(この国で休ませた・外した学びを除く)+ 人が付けたもの − 人が外したもの。付け外しは表 `card_learnings`。X78)、**商品の MD 方針**(`setActivePolicies`。商品の候補の `md` に段階・方針・販促の予定と期間を付け、そのときだけ `MD_NOTE` で使い方を伝える。バックログ M2)。

### 2.2 指示文(プロンプト)

- `aiSelect.ts`(セクション、商品、メイン画像)と `aiDraft.ts`(テーマ、コピー、制作指示、テンプレートの選択)に、日本語で書いてある。
- **出力の言語**: 画面が English のときは、`localizePrompt` が、指示文の「日本語で書く」を「英語で書く」に置き換え、文字数の上限を英語の長さに直す。コピーとヘッドラインの言語は、別(`language`: auto / ja / en。auto は、配信カードの国に従う)。
- 商品・メイン画像は、AI に渡す前に、**配信カードの国に合う市場(JP / US)のものだけ**に絞る(`CardDetail.tsx` の `poolProducts` / `poolHeroes`)。

### 2.3 チャット(`src/ChatPanel.tsx`、`aiSelect.ts` の `withChat`)

- 開いているタブの案づくりに、ユーザーの指示と、これまでの対話(最大 12 発言)を加えて、同じ「案を作る」処理を呼び直す。
- AI は、発言が質問・相談のときは `mode: "answer"` で答えだけを返し(案は変えない: `ChatAnswer` を投げて、呼び出し側が無視する)、作り直しの依頼のときは `mode: "update"` で案と `reply` を返す。
- 会話は、画面を開いている間だけ保持する(保存は未実装。[BACKLOG.md](BACKLOG.md))。

### 2.4 すべてAIで下書き(`src/autoDraft.ts`)

テーマ → テンプレート + メイン画像 → ヘッドライン・コピー → 各セクション(順に)→ 制作指示。結果は画面に反映するだけで、保存はしない。

週の枠からまとめて AI で中身を作る(W14。`src/bulkDraft.ts`・作業画面の `src/useBulkWorkspace.ts`)も、同じ `runAutoDraft` を使う(作り方を、配信カードとずらさないため)。保存は、配信カードの保存(`buildContent`・`syncItems`)と同じ形にそろえる。配信カードの保存の形を変えたら、`bulkDraft.ts` の `contentFields`・`saveProducts`(週の枠に書き込む `applyResult` と、作業画面で新しく保存する `createDraft` が使う)も直す。まとめて作る作業画面(`src/useBulkWorkspace.ts`・`src/BulkWorkspace.tsx`)は、中身のない枠を保存せず、中身ができた配信から「未起案」で新規作成する。

## 4. データの読み書き(`CardDetail.tsx`)

- 配信カード: 表 `delivery_cards`。AI の理由・切り口(`theme_reason` など)、セクションの見出し(`section_titles`)・コピー(`section_copies`、JSON)も、ここに保存する。

- 週の枠からまとめて中身を作る(W14)ときは、人が「中身を作る」を押すことを、AI の第 1 候補の採用とみなして保存する。配信カードの「AI で下書きする」(空のカードのプレビューの真ん中・すべてAIで下書き・テンプレートが見つからないときの下書きし直し)も、押したことを採用とみなし、済んだらふだんの保存の道(`saveStaying`。元に戻すの履歴にも積む)で保存する(2026-10-27 利用者)。空のカードを開いただけでは、AI は始めない。開いたときに自動で始まる下書きし直しと、まだ作っていない案・確定した週の配信は、自動では保存しない。人の確認は承認で担う(承認されたことを、人が確かめたことと同じとみなす。2026-10-24 利用者と決め、「AI 下書き・未確認」の印 `ai_unchecked_at`・「確認した」・確かめる引き出しはやめた = SU7)。使わなくなった列は `server/schema.json` の `retired` に書き、書き込みに来ても断らずに無視する(古い画面・前に書き出したパックのため。DB の列は自動では消さない)。
- まとめて作る作業画面(`BulkWorkspace`)は、AI の案を保存せずに画面だけに持ち、人が 1 本ずつ「保存」したものだけを、ふつうの下書き(未起案)で保存する(未確認の印は付けない。保存しなかった案は破棄)。週の表示で枠(破線)として出すのは、「この週の枠を作る」で作った配信(`frame_at`)だけ。
- 商品・カテゴリの週の指標(X48): 表 `product_metrics` / `category_metrics`(1 行 = 商品(カテゴリ)× 週 × 項目)。値は、外で計算し終えたもの(順位・WoW・MoM・YoY まで)を持ち、**画面では計算しない**(母集団・暦の月の数え方を、取り込む側の 1 か所で決めるため)。取り込みは CSV(⚙、または `ccp.cli import-metrics`。`server/ccp/metrics.py`)で、週 × 市場ごとに置き換える。あとで BigQuery からの取り込みに替えても、表と置き換え方は同じ。定義と形は [METRICS_FORMAT.md](METRICS_FORMAT.md)。
- 商品の販売順位(R17): 表 `product_rankings`(1 行 = 商品 × 週 × 販売チャネル(全社 / EC / 配信経由))。BigQuery の出力 `ranking` から週ごとに置き換えて取り込む(`server/ccp/bq_import.py`)。取り込むまでは `ccp.cli ranking-dummy` のダミー(`as_of` が空)。上位とみなす線 Top N は、ブラウザごと(`rankingSettings.ts`)。
- 外部広告の出稿(X49): 表 `ad_spends`(1 行 = 1 日・1 商品・1 媒体)。いまは見本だけ(`/api/ads/sample`。`campaign` が `sample:` で始まる行)。あとで BigQuery か CSV から取り込む。見せ方「商品別」(`ProductsView.tsx`)が読む。
- 制作の依頼(PR2〜): 表 `production_requests`(配信 1 本の 1 版)。画面から直接書かず、`/api/production`(`server/ccp/production.py`)だけで進める(承認済みかの確かめ・版の数え方をサーバーでまとめる)。設計は [PRODUCTION.md](PRODUCTION.md)。やり取りへのリアクションは表 `note_reactions`(状態は変えない)。
- 選択肢(ステータス、チャネル、カテゴリなど)は、文字の値(例: `email` / `app`)で持つ。表示名(`○○_name`)は、`labels.ts` が、値から補う。状態の前後は `statusRank` で比べる(文字のまま `<` で比べない)。
- **承認の流れ(2026-10-14 決定。2026-10-17 の U1〜U6 で、下の「ユーザーと承認」の形に変えた。データの値と `statusRank` の順はそのまま)**: データの値は、配信が 未起案(not_started)→ 検討中(reviewing)→ 承認済み(approved)→ 確定(confirmed)、週が 下書き(draft)→ レビュー中(review)→ 確定(confirmed)。**画面では**、配信を 未起案 / 承認待ち / 承認済み(+ 確定した週は鍵マーク)、週を 確定前 / 確定 と見せる(`src/status.ts` の `statusView`・`statusLabel`、`LockMark`)。
  - 承認は、配信 1 本ずつ(配信カードの「保存して承認」)と、週まとめて(週の帯の「まとめて承認」= 検討中をすべて承認済みに)の両方。誰でも押せる。
  - 差し戻しは、理由が必須。配信は検討中になり、理由はレビューのコメント(未対応)にも残す。
  - 承認済み・確定の配信の内容を変えて保存すると、検討中に戻る(再承認が必要)。変わったかは、開いた時点の内容と比べる(保存済みの行と比べると、表し方の違いだけで変わったことになるため)。確定した週の配信は、理由つきの確定後の変更(W3)の流れになる。
  - 確定は、週単位(「週を確定」)。「承認済み」(内容が OK)と「確定」(制作に回してよい)は、分けて残す。
  - 「誰が」は、ログインで人を見分けないので、画面で入れた名前(`me.name`)。操作は、操作の履歴(`events`)に残す。通知はしない。
- **ユーザーと承認(2026-10-17 決定。設計は [APPROVAL.md](APPROVAL.md)。バックログ U1〜)**: 配信カードごとに承認を依頼し、承認グループ(だれか 1 人で済み)・人が承認する形に変えていく。決まりは全員 / 1 人、自分の依頼は承認できない、1 人でも差し戻したら止める、1 回の承認は 1 グループ分。通知はメールが飛ぶ前提で送る箱に積む。上の W9 の流れは、U4 ができるまで残す。
  - ユーザーマスタ(`users`。メールアドレスが本人を見分けるかぎ)と承認グループ(`approval_groups`・`approval_group_members`)は、⚙ →「ユーザーと承認グループ」(`PeopleManager.tsx`)。読み込みは `people.ts`(画面全体で 1 回。編集したら `reloadPeople`)。ログインが入るまでは、だれでも編集でき、変更は `events` に `user_change` / `group_change` で残す。
  - 「あなた」= ログインしている人(U9。2026-10-19)。右上の `MePicker`(アカウントの見た目。押すと「ユーザーを切り替える(デモ)」)で選んだ人を、ログインしている人とみなし、ほかの画面(承認のブロック・やり取り・ユーザーと承認グループ)では人を選ばせない。初回は `SignInDialog` で選ぶ。本物のログイン(U7)が入れば、切り替えが消えるだけ。ユーザーがいなければ、これまでどおり名前を入れる。記録は、これまでどおり名前の文字(`me.name`)で残す。
  - 承認の依頼・承認・差し戻し・取り下げは、サーバーの窓口 `/api/approvals`(`server/ccp/approvals.py`)だけで行う(配信カードの `ApprovalBar`、週の帯の `weekApprovals.ts`)。判定は `src/approvals.ts` と同じで、`server/tests/approval_cases.json` の例を両方で確かめる。通知は送る箱 `notifications` に積むだけ(送る仕組みは未実装)。ヘッダーの「依頼」は、依頼中の依頼から計算する(`useApprovalInbox`)。

## 5. テンプレート(`src/templates.ts`、`layoutTemplates.ts`)

- **標準の 10 種**は、コードに持つ。画面から編集すると、`layout_templates` の上書きの行(`overrides` = 標準の ID)で置き換わり、「最初の形に戻す」で上書きの行を消す(コードの標準は変わらない)。以前からの 6 種(free, standard4, collab, offer, cat2, cat3)と、新しい部品を使う 4 種(sale, spotlight, story, editorial)。
  - 以前からの 6 種は、**コードの定義の**セクションの構成を変えない(画面からの編集は、下の「使ったときに写す」で守られる)。保存済みのカードは、商品をセクションの順に流し込み、見出し・コピーもセクションの番号で持つので、構成を変えると位置がずれる。見た目の設定(ヘッドラインの見せ方・ボタン)だけ変えてよい。
  - 新しい 4 種は、以前の選択肢の列(`emailtemplate`)に値がないので、`layoutkey` だけで指す。
- **セクションの部品**(`Section.kind`): grid(名前・価格つき。2 / 3 列)、photos(写真だけ。2 / 3 列)、wide(全幅で大きく 1 点ずつ)、mosaic(大 1 点 + 小 2 点で 1 組。枠は 3 の倍数。`flip` で大きい枠を右に)、story(写真と商品の説明を左右交互)、feature(特集)、cells(画面では「箱」。`cols` 1〜4 と、枠の並び `cells` = {c, r, w, h}。いくつかのマスを 1 つの枠にまとめられる。**枠の配列の順が商品の載る順**(初めは上から・左から。画面で入れ替えられる)で、`slots` は枠の数。見せ方 `view`: card(省略。写真 + 名前・価格)/ photo / detail(写真の横に説明)/ story(左右交互)。形の処理は `cells.ts`。以前の版のアプリは、知らない種類をグリッドとして `slots` で読むので、商品の位置はずれない)、**table(表。T8。列 1〜4 × 行 1〜8 のマスに、部品 `parts` = {id, type: box / button / text / empty, c, r, w, h, 種類ごとの設定} を敷き詰める。箱 1 つ = 商品 1 点で、載る順は上の行から・同じ行は左から。部品 ID は形が変わるまで変えない。操作は `tables.ts`、編集画面は `TemplateTableEditor.tsx`。テンプレートの編集は表だけで行い、以前の種類は開いたときに `toTableLayout` で表に直す(保存済みの版はそのまま描く)。設計は TEMPLATE_OBJECTS.md)**。どの部品にも、見出し(`categoryHeading`)を付けられ、コピーを外せる(`copy: false`。省略はコピーあり)。
- **ボタンの部品**(`ButtonBlock`): セクションとは別に、`buttonBlocks`(`at` = その前にあるセクションの数。0 はヒーローの直後)で持つ。商品の枠の位置の計算(`sectionsOf` など)は、セクションだけを見るので、ボタンを足しても、商品・見出し・コピーの位置はずれない。
  - ボタン(`ButtonSpec`)は、変わらない `id`、文言(`label`。空は既定の文言)、見た目(`style`: fill / outline)、リンク先の種類(`link`: campaign / category / top / custom)を持つ。**`id` は、配信カードでボタンごとの URL を持つときの鍵**にする(文言や位置を変えても、URL が外れないように)。
  - 以前の形(ヒーローの `heroButtons`、セクションの `buttons`)も読む。描画は `placedButtons` が、以前の形を、位置 0 / セクションの後のボタンの部品に直して、まとめて返す。管理画面で開くと、部品に置き換わり、保存すると以後は部品として持つ(標準のテンプレートは、以前の形のまま)。
- **ヒーローの見せ方**(テンプレート全体): `heroText`(band: 写真に帯で重ねる / overlay: 写真に大きく重ねる / below: 写真の下)、`heroLink`(画像のリンク先の種類)、`topBar`(お知らせ帯)。
- **リンク先**は、テンプレートには種類(既定値)だけを持つ。実際の URL と計測用のパラメーターは、配信カードの `links`(JSON。`src/links.ts`)に持つ。
- **計測用のパラメーター(UTM)の決まり**(X67。`src/links.ts` の冒頭): `utm_campaign` = どの配信か(`campaignId`: 配信日 YYYYMMDD + 配信カードの ID の先頭 8 文字。AB テストは末尾に `-a`・`-b`・`-c`)、`utm_content` = その配信の中のどのリンクか(`hero` / `btn<n>`(ボタン。`placedButtons` の順 = メールの上から。1 から)/ `p<nn>-<商品コード>`(商品の枠。セクションをまたいだ通しの番号を 2 桁。商品コードは大文字・小文字をそのまま))。content は位置と商品コードをそのまま書くので、GA から取り込むときに対応表は要らない(最初の `-` までが枠)。結果の `positionShares` のキー(hero・button:i・slot:i)と数え方が同じ。リンク先のページの名前(`/campaign/<配信名-日付>`)とアプリの通知の data の `campaign` は、これまでどおり `campaignSlug`。
- **版 3(2026-10-26。T8 の 8.10)**: 表のテンプレートの部品は、`utm_content` に**押された要素の ID**を入れる(読みやすい名前・短い番号は使わない)。メイン画像は `sec_hero.image`、ボタン・画像は `partContent`(要素が 1 つなら要素の ID `btn_7d2a.label`・`med_x1.image`、画像の上に文字のボタンのように部品まるごとが 1 つのリンクなら部品 ID `btn_7d2a`)。**表の箱は、押せる要素(`elementClickable`。既定は写真・名前・ボタン)ごとに別のリンク**(`box_2m8q.image`・`box_2m8q.name`。`productLinks`。書き出す HTML は、箱の中の `data-el` を `<a>` で包む)。以前の形のセクション・標準のテンプレートは、版 3 でも版 2 の形(部品 ID がないため)。説明は UTM に入れず、`elementDescriptions`(ID → 説明)から引く対応表に出す(制作のページの「計測の対応表」・`trackingRows`)。テンプレートの部品の「計測用の名前」(`track`)はやめた(保存済みの値は読んで残すが、URL には使わない)。読むのは `results.ts` の `parseContent`(新旧どちらも)と `linkResultsFromContents`(配信のテンプレートの版で、要素の ID をヒーロー・何番目のボタン・何番目の商品の枠に引き、`links.els` に要素ごとの数も残す)。例は `scripts/check-utm.mjs`(verify に含む)。
- 制作の依頼の写し(`Snapshot`)は `utm`(作り方の版。いまは 3)を持つ。版のない古い写しは、これまでの作り方(campaign = 配信名 + 日付、content なし)で URL を出し、版 2 の写しは表のテンプレートでも hero・btn・p01 のまま(もう送った配信の URL を、画面の上で変えないため)。UTM の作り方を変えるときは、版を上げて、古い版の作り方を残す。
- **テンプレートの部品の、配信ごとの中身**(T8 段階 6。設計は [TEMPLATE_OBJECTS.md](TEMPLATE_OBJECTS.md) の 6.1): 配信カードの列 `part_content`(部品 ID → 文・画像。`src/partContent.ts`)。テンプレートで許した部品(テキストの `overridable`、画像・動画の `swap`、画像のボタン)だけ差し替えて描く(`effectivePart`)。保存は、いまのテンプレートにある書き換えてよい部品の分だけ(`prunePartContent`)。AB の案ごとに、案の文言 `VariantText.parts` に持つ(A は列)。見出し・コピーは、いまの列(セクションの番号)のまま。載せた商品の `delivery_products.part_id` は分析のために書くだけで、画面は読まない。新しく部品の中身を描く所を足したら、`partContent` を渡す。
- 見取り図(`TemplateThumb.tsx`)は、実際のメールに近い縦横比で、縦長に描く。一覧では上の部分だけ(`maxHeight`)、管理画面では全体を表示する。
- **ユーザーが作ったテンプレート**は、テーブル `layout_templates` に保存する(名前、説明、ヒーローの種類、セクションの JSON)。アプリの起動時に読み込み、`setCustomTemplates` で登録する。
  - ヒーローの見せ方は、列がないので、セクションの JSON の先頭に `{"kind":"hero",...}` として入れる(`layoutTemplates.ts`)。ボタンの部品は、置く位置に `{"kind":"buttons","buttons":[...]}` として挟む。どちらも `slots` を持たないので、以前の版のアプリは読み飛ばす(ボタンが出ないだけで、商品の位置はずれない)。知らない部品(`slots` あり)は、グリッドとして読む。
  - 既定の値は書かない。ヒーローが既定で、ボタンの部品もないテンプレートは、以前と同じ形(セクションの配列だけ)になる。
- 配信カードは、`layoutkey`(標準は ID、作ったものは行の GUID)でテンプレートを指す。標準のテンプレートは、以前の選択肢の列(`emailtemplate`)にも書く(互換)。`layoutkey` が空なら、選択肢の値から決める。
- **テンプレートは版で持つ**(配信のもとになるマスターなので。2026-10-21 利用者と決めた): 保存するたびに新しい版になり、表 `layout_template_versions`(テンプレートの ID・版の番号・中身・メモ・保存した人)に 1 行増える。`layout_templates` の行は、いまの版の中身と番号(`current_version`)を持つ。標準は、コードの定義が版 0 で、編集すると上書きの行(`overrides` = 標準の ID)が版 1・2… を持つ。
  - 配信カードは、`layout_key`(テンプレートの ID。版で変わらない)と `layout_version`(使った版の番号)を持つ。描画は、`templateKeyOfCard` で「ID」(いまの版)か「ID@v版」(過去の版)の鍵を作り、`getTemplate(鍵)` で引く(`sectionsOf` など、鍵で動く仕組みはそのまま)。版を管理する前の配信(`layout_version` が空)は、いまの版として描き、テンプレートを初めて編集する前に、いまの版の番号を書き込む(`saveTemplate`)。
  - 配信カードで保存するときは、鍵を ID と版の番号に分けて書く。いまの版のテンプレートを選んだときは、いまの版の番号。
  - テンプレートごとの集計・一覧は `layout_key`(`templateIdOfCard`)、版ごとは `layout_version` でまとめる。
  - 前の版に戻す・標準を最初の形に戻すは、その中身を新しい版として保存する(履歴を消さない)。
- **使わない(無効)**(`hidden_at`): 配信カードの選択肢に出さない(使っている配信は、そのまま)。標準を使わないにするときは、中身が同じ上書きの行に印を付ける(中身が標準と違うときだけ「編集済み」)。**削除**は、どの版もどの配信でも使っていない、作成したテンプレートだけ(版の行も消す)。
- 登録にない ID(削除された、まだ読み込まれていない)は、Standard4 として扱う。
- 管理の画面は、ヘッダーの「テンプレート」ボタン、または、配信カードの「②テンプレート」タブから開く(`TemplateManager.tsx`)。

## 6. 日本語・英語(`src/i18n.ts`)

- **画面の文言は、その場に `t('日本語', 'English')` と書く**(コンポーネントの先頭で `const t = useT()`)。React の外では `tr('日本語', 'English')`。辞書ファイルは使わない。日本語だけの文言を、画面に書かない(例外は、開発する人だけが使う開発用の画面 `/dev/`(`src/dev/`)。日本語だけでよい。[DEVTOOLS.md](DEVTOOLS.md))。
- モジュールの最上位に、日本語の文言を持つ定数を置かない(言語を切り替えても変わらなくなる)。関数にするか、getter(`get label() { return tr(...) }`)にする。
- 日付・数値は `locale()`、価格は `yen(price, market)`(US の商品はドル、JP の商品は円)。
- 選択肢のラベル(日本語)は、`optionLabel(label)` で、表示だけ英語にする(値は変えない)。辞書は `i18n.ts` の `OPTION_EN`。
- 商品・メイン画像は、`market` 列(JP / US)で区別する。空は JP とみなす(`market.ts`)。US の商品の画像は、同じイラストを使い回す(`images.ts`)。
- **配信ごとに選んだ商品の画像(X64)は、配信に載せた商品の行(`delivery_products.image_url`)に持つ**(商品のマスタ `products.image_url` は変えない)。画面では `Item.imageUrl` に載せ、描くところは `productImage(p, it.imageUrl)` を使う(プレビュー・商品情報の行)。制作のページは、写しの商品の `image_url` にその画像を入れて持つ(App の `cardImages`。依頼したあとは、そのときの画像のまま)。商品を差し替えたら、画像は外す。

## 9. 落とし穴(過去にはまったこと)

- CSS の `zoom` を使う箇所(`items.ts` の `scaled`、プレビューの倍率)では、**幅を `%` で補正しない**(現在のブラウザの仕様では、枠より広がる)。
- Fluent の `Switch` の色は、ヘッダーのような色付きの背景では、効きにくい(ヘッダーのトグルは自作)。
- Fluent の `Textarea` には最低の高さがある(`AutoTextarea` で解消している)。
- 列を変えたら、`server/schema.json` と画面の型(`src/models/`、一部の表は `src/data/`)を一緒に直す(`npm run verify` が食い違いを見つける)。
- 改行コードは、すべて LF(2026-10-23。以前は CRLF と LF が混ざっていた)。`.gitattributes` の `* text=auto eol=lf` で、Git に入るのは LF になる。Windows のエディタやスクリプトが CRLF で書き出すと、差分がファイル全体になり、ほかのセッションの変更とぶつかる。

## 描画の失敗で真っ白にしない(2026-10-23)

- `src/ErrorBoundary.tsx` で、画面の中身(App の面・見せ方の部分)・配信カード・全体(Root)を囲む。失敗した部分だけを、理由と「もう一度」(配信カードは「閉じる」も)のお知らせに置き換える。画面・見せ方・配信を移ると描き直す。
- 一覧・月の画面が呼ぶ共通の関数(`sectionsOf` など、App の計算の中で動くもの)は、境界では救えない(App ごと置き換わる)ので、データの形が違っても投げないように書く。テンプレートは形が変わり続けるので特に。
