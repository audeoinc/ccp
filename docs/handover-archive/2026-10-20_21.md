## 6.46 テンプレートの管理: 版管理・標準も編集・使わない(無効)(2026-10-21、ローカル、ブランチ feature/template-versions)

- 利用者の課題: 標準のテンプレートがそのまま編集できない(複製してからの編集だけ)、削除できない。一般的な配信ツールのやり方(テンプレートは使い始めの型、版・アーカイブ)と照らして、**テンプレートは配信のもとになるマスターなので、版で持つ**ことに決めた。最初に作った「編集の前の形の写しに付け替える」方式は、ID でテンプレートを識別できないのでやめた(push 前に作り直した)。
- **版**: 表 `layout_template_versions`(テンプレートの ID・版の番号・中身・メモ・保存した人)。保存するたびに 1 行。`layout_templates` に `current_version`。標準は、コードの定義が版 0、編集は上書きの行(`overrides`)が版 1・2… を持つ。
- **配信**: `delivery_cards` に `layout_version`(使った版)。描画は `templateKeyOfCard` の鍵(「ID」か「ID@v版」)で `getTemplate` を引く(過去の版も、登録に「ID@v版」で入れてある)。編集しても、すでにある配信は使った版のまま。版を管理する前の配信は、テンプレートを初めて編集する前に、いまの版の番号を書き込む。配信カードで保存すると、ID と版の番号を書く。
- **管理の画面**: 標準も作成したものも「編集・複製・使わないにする(使っていなければ削除)」。詳しい欄に「いまの版: 版 n」、**版の履歴**(版ごとの日付・人・メモ・使っている配信の数、「見る」「この版に戻す」)、**使っている配信**(版ごとに、配信名・日付・状態。押すと配信カード)。編集中は「変更のメモ」の欄と、使っている配信があれば黄色の帯。保存の前に「版 n+1 になる。これらの配信は使った版のまま」と確かめる。標準の「最初の形に戻す」・「この版に戻す」は、その中身を新しい版として保存する。
- **使わない(無効)**(`hidden_at`): 配信カードの選択肢から外す(使っている配信は、そのまま)。一覧の下の「使わないテンプレート(n)」から「また使う」。削除は、どの版もどの配信でも使っていない、作成したテンプレートだけ(版の行も消す)。以前の「削除すると、使っている配信が Standard4 になる」動きはなくした。
- **配信カード**(② テンプレート): 前の版を使っている配信に「このテンプレートは、この配信のあとに編集されました(この配信は版 k、いまは版 n)」と「いまの版(版 n)にする」。使わないテンプレートを使っている配信にも、その旨。
- 確かめたこと: `tsc`・`eslint`・`build`・`verify`。デモで、標準 Standard4(1 本で使用)を編集(メモつき)→ 版 1 になり、使っている配信は版 0 のまま(版の履歴・使っている配信の一覧)→ その配信のテンプレートのタブに知らせと「いまの版(版 1)にする」→ 管理の画面で「この版に戻す」(版 0)→ 版 2「版 0 に戻した」、札は「標準」に戻る。使わない・削除は、写しの方式のときに確かめた動きのまま(言葉を「使わない(無効)」にした)。
- 確かめていないこと: 本番(表と列の追加)、「いまの版にする」を押して保存したあと、アプリのテンプレート、英語の画面、ログインしている人がいるときの「保存した人」。
- 次(利用者と決めた): 配信カードで構成を変えて、その配信だけの形として持つ(テンプレートに戻す / 新しい版にする / 新しいテンプレートにする)は、別のブランチで。
- **本番に入った(2026-10-21 12:53、別のセッションの反映 `deployed-gcp/20261021-125305`、main 8f98890。こちらのマージ b764aff を含む)。**本番の画面での操作と、表・列の追加は、まだ確かめていない。

- **BigQuery の取り込みを手元で試すとき**: 手元に PostgreSQL がない。作業用のフォルダに `npm i @electric-sql/pglite @electric-sql/pglite-socket` を入れ、`pglite-server -p 55432 -m 8` で起動し、`DATABASE_URL=postgresql+asyncpg://postgres:postgres@127.0.0.1:55432/postgres?ssl=disable`。PGlite は 1 つの裏側を接続で共有するので、asyncpg の準備済みの文の名前がぶつかる。初期データの投入とサーバーの起動を 1 つのプロセスで行い、`create_async_engine` に `connect_args={"prepared_statement_name_func": ...}`(一意の名前)を渡す(起動用のスクリプトだけで行う。本番のコードは変えない)。BigQuery は `CCP_DEV_GCLOUD=1`(手元の ADC は再認証が要る状態だった)。
- **`progress.ts` は改行が CRLF**、ほかの多くは LF(`App.tsx` は、以前は CRLF だったが、いまは LF。2026-10-15 に確認)。スクリプトで書き換えるときは、決めつけずに、読み込んだファイルの改行コードを保つ。
- ツールで書いた文字列に、目に見えない BOM(`U+FEFF`)の文字がそのまま入ることがある(lint の `no-irregular-whitespace` で落ちる)。コードでは `String.fromCharCode(0xfeff)` と書く。
- Fluent の `DialogBody` は、中を独自の列に並べる。広いフロートの中を自分で並べるときは、`DialogBody` を使わずに `div` にする。
- Fluent の `makeStyles` は、`borderWidth` / `borderStyle` のような短い書き方を受け付けない。描くときに決める線は、`style` に書く。
- 本番のデータを直すときは、API を Basic 認証で呼ぶ(パスワードは Secret Manager の `contents-planner-app-password`)。手順は [GCP.md](../GCP.md)。
- **DB(Cloud SQL)の起動・停止(2026-10-16 に利用者が決定)**: 起動は、画面を開いたときの自動起動だけ(10〜13 分かかる)。動き出したら、毎晩 21:00 の停止(`ccp-stop-db-nightly`)か、明示的な指示まで動かしておく。30 分使わないと止める `ccp-idle-check` と、朝 8:00 に起動する `ccp-start-db-3days` は、一時停止(PAUSED)にしてある(消していない。戻すなら `gcloud scheduler jobs resume <名前> --location asia-northeast1`)。

- **本番への反映のビルドは、`cloudbuild.yaml`(kaniko。層のキャッシュ)で行う**(2026-10-19 から)。Dockerfile の 1 段目は、画面のビルドに要るファイルだけを入れる(`index.html`・`vite.config.ts`・`tsconfig*.json`・`public`・`src`)。**画面のビルドが、ほかの場所のファイル(例: `docs/` の CSV)を読むようにしたら、Dockerfile の COPY に足す**(足さないと、クラウドのビルドで、そのファイルがない)。キャッシュつきのビルドが失敗すると、スクリプトは `--source`(キャッシュなし)に切り替えるので、反映は遅いが止まらない。ほかの人の反映(同じサービスの Cloud Build)が進行中なら、終わるまで待ってから確かめ直す。くわしくは [GCP.md](../GCP.md) の「反映の速さ」。
