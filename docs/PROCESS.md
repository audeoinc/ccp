# 前提とする運用プロセスと、今の運用との照らし合わせ

CCP の機能は、ある運用の流れを前提にしている。使う人にこの流れを先に伝え、使ってみてもらい、合わないところを確かめて直す(2026-10-19、利用者と決めた)。
この資料で、次の 2 つを見えるようにする(2026-10-20 に強化)。

- **どの業務が、どう良くなるか**: CCP の前提運用(3 章・7 章)に、今の運用を照らし合わせ、差があるところを見る。差は、運用を CCP に合わせれば良くなるところか、CCP を直すところのどちらか(3〜4 章)。
- **要らない機能はないか**: 機能を「流れの芯 / 良くする / 要検討」に分け、重なっているもの・前提が合わないかもしれないものを挙げる(5 章)。

進め方は、**① CCP の前提運用を見せる → ② 今の運用を聞いて照らし合わせる → ③ 差があるかを付け、差の扱いを決める**。今の運用(As-Is)は、まだ聞いていない(2026-10-20 時点)。聞き取りでは、3 章・5 章・6 章・7 章をまとめた**照らし合わせのシート**<!-- hosted:begin -->(CCP の ⚙ →「前提運用の照らし合わせ」。開発元の本番の画面)<!-- hosted:end -->を使う。聞き取り先ごとに、入力するとその場で保存され、差の数を段階ごとに数える。結果は 3.8 に書く(8.1)。

この文書は、利用先に渡す資料にもなるので、社内のシステムの名前・本番の環境の名前は書かない。

- 承認のしくみの設計は [APPROVAL.md](APPROVAL.md)、制作の依頼の設計は [PRODUCTION.md](PRODUCTION.md)、画面の導線は [FLOWS.md](FLOWS.md)。
- 機能の番号(F01 など)は、[FEATURE_REASONS.md](FEATURE_REASONS.md)(機能の理由の台帳)の番号。業務の作業・確認は [USER_STORIES.md](USER_STORIES.md)。

### 印

| 印 | 意味 |
|---|---|
| 差なし / 差あり / 業務はない | 照らし合わせの結果。**差なし** = 今も前提どおり、**差あり** = 今の運用が違う、**業務はない** = 今その業務をしていない(機能が要らないかもしれない) |
| CCP に合わせる / CCP を直す / 保留 | 差の扱い。**CCP に合わせる** = 運用を前提に寄せる(それで良くなる)、**CCP を直す** = 前提のほうが合っていない |
| 時間 / 質 / 事故 / 記録 / 新規 | 差があって、運用を CCP に合わせたときに良くなることの種類(3 章)。**時間** = 手間が減る、**質** = 判断がそろう・根拠が見える、**事故** = 配信の間違いを前に防ぐ、**記録** = だれが・いつ・なぜが残る、**新規** = 今はできていないことができる |

## 1. 流れの全体

| # | 段階 | 何を決めるか | 主に動く人 | 画面 |
|---|---|---|---|---|
| 1 | 起案 | 何を配信するか(テーマ・メイン画像・ヘッドライン・コピー・商品) | 企画(マーケの担当) | 計画(Plan)の配信カード |
| 2 | 承認 | 配信の中身でよいか | 承認者(承認グループのだれか) | 計画の配信カードの右端(状態と承認) |
| 3 | 制作への依頼 | どう見せるかを、制作に頼む(制作指示・担当・締め切り) | 企画 | 制作(Production)の面・制作のページ |
| 4 | 制作 | 見せ方(メール・アプリの仕上がり) | 制作の担当 | 制作のページ |
| 5 | 仕上がりの確認 | できたものでよいか。よければ「これで OK」、だめなら「直してほしい」で制作に戻す | 企画 | 制作のページ |
| 6 | 配信 | 配信のしくみに入れて送る | 企画・制作 | (配信のしくみ。CCP の外) |
| 7 | 結果 | 送ったあとの数字と学び | 企画 | 結果(Results)の面 |

- 1〜2 は「**何を配信するか**」の話で、企画とその関係者(レビュー・承認する部署)のやり取り。
- 3〜5 は「**どう見せるか**」の話で、企画と制作のやり取り。
- Plan・Production・Results は、**同じカレンダー(配信日)**の表・中・裏。同じ配信が、どの面でも同じ日・同じ位置に出る。
- 流れの外で起きること(在庫切れ・方針や日程の変更・取りやめ)は、**アラート**で知らせ、その配信の段階に戻して直す。

## 2. 段階の名前は「いま、だれの番か」で言う

状態だけを言う名前(「承認済み」「引き継ぎ済み」)は、見る人によって意味がぶれる。次に動く人を添えて言う。

| 面 | 状態 | 次に動く人 |
|---|---|---|
| 計画 | 未起案 / 企画を作っている | 企画 |
| 計画 | 承認待ち | 承認者 |
| 計画 | 承認済み(週が確定すると鍵) | — (制作へ) |
| 制作 | 制作に依頼する前 | 企画 |
| 制作 | 依頼済み(受け取り待ち) | 制作 |
| 制作 | 制作している | 制作 |
| 制作 | 制作が終わった | 企画(仕上がりの確認) |
| 制作 | 制作を通さず、配信のしくみに送った | 企画 |

## 3. 業務ごとの前提運用(照らし合わせの元)

業務ごとに、CCP が前提にしている運用と、**今の運用に差があったとき**、運用を CCP に合わせると何が良くなるかを書いた。差がなければ、その業務は良くも悪くもならない(CCP を入れる理由にならない)。
今の運用と差の有無は、聞き取りで埋める(3.8)。C5 は CCP の外に残る(4 章)。

## 4. 変わらないこと・新しく増える手間

良くなることだけでなく、増える手間も並べておく(使い始める前に、利用先と合意する)。

| 種類 | 内容 | 減らす手立て |
|---|---|---|
| 変わらない | 配信のしくみに入れて送る作業(C5)。配信の結果を、配信のしくみから取り出す作業 | 配信のしくみとつなぐ(バックログ) |
| 増える | 商品・在庫・売上・方針のデータを取り込む。古いと、AI の選定とアラートが外れる | 定期の取り込み([BIGQUERY.md](BIGQUERY.md)・[POLICY.md](POLICY.md)) |
| 増える | 結果の CSV を取り込む(E1) | 配信のしくみとつなぐ(バックログ) |
| 増える | 状態を進めるボタン(承認の依頼・承認・週の確定・制作の依頼・受け取った・制作が終わった・これで OK)を押す | 段が多すぎないかを確かめる(5 章) |
| 増える | AI の案を確かめる。AI には費用がかかる | 案には理由を付けて、確かめやすくしてある |
| 増える | 知らせが来ないので、自分の番かどうかを画面に見に行く(ヘッダーの「依頼」の件数・担当の「自分」) | メール・チャットへの通知(バックログ) |
| 二重になる | 使い始めは、今の資料・やり取りと CCP の両方を持つことになりやすい | 何を CCP に移し、何をやめるかを、始める前に決める(8 章) |

## 5. 機能の要否の棚卸し

機能を 3 つに分ける。**要検討**は、使ってみて要らなければ外す・まとめる候補。

| 分け | 意味 |
|---|---|
| 芯 | ないと、1 章の流れが回らない |
| 良くする | なくても回るが、3 章の「良くなること」を生む |
| 要検討 | 別の機能と重なっている、または前提が合わないかもしれない |

### 5.1 芯

- 計画のカレンダーと配信カード(F01, F07, F08)、状態の色(F02)
- 配信の中身: テーマ・テンプレート・メイン画像・文言・セクション・商品・リンク先・制作指示(F18, F21, F31, F33, F37, F40, F65, F61)
- 承認の依頼・承認・差し戻しと履歴(F73)
- 制作の面と制作のページ(F111)
- 国ごとの商品・画像・言語(F32, F34)

### 5.2 良くする

- AI の下書き・選定と理由(F14, F30, F39, F12)、AI チャット(F48)
- 商品情報のペイン(F45, F47)、プレビュー(F52〜F58)
- 週の表示と「確定の前に直すこと」(F68, F71)、コメント(F72)
- アラート(F88〜F94)
- 結果の面と、次に生かすメモ(F77〜F85, F103)
- リンクをコピー(F106)

### 5.3 要検討

| # | 機能 | なぜ要らないかもしれないか | 確かめること | 要らなければ |
|---|---|---|---|---|
| R1 | 週の確定(F69, F70)と、配信ごとの承認(F73)と、配信の状態(F02) | 「承認済み」と「確定」の 2 段がある。配信ごとに承認するなら、週の確定は重いかもしれない | 週で区切って締める場面が、今の運用にあるか | 週の確定をやめ、配信ごとの承認だけにする |
| R2 | 制作への「引き継ぎ」のタブ(F66: 担当・締め切り・引き継ぎ済み) | 制作のページの「制作に依頼する」(F111)と役目が重なる。担当・締め切りを 2 か所で持つ | 制作の依頼を使い始めたあと、引き継ぎのタブを使う人がいるか | 引き継ぎのタブを外し、制作の依頼にまとめる |
| R3 | 下書きの入口が 3 つ(すべてAIで下書き F14・開いたとき自動で下書き F15・まとめて AI で作る F76) | 入口が多いと、どれを使うか迷う | どの入口が使われているか | 使われない入口を外す |
| R4 | 週の資料の PDF(F74) | 画面の中でレビューするなら、資料は要らない | 画面を開けない人(役員・他部署)に見せる場面があるか | 外す |
| R5 | 詳しい結果の PDF(F86) | 結果の共有を、リンク(F106)で済ませられるかもしれない | 結果を社外・画面を開けない人に渡すか | 外す |
| R6 | 制作の工程の「受け取った」(② の段) | 依頼 → 制作 → 確認の間に 1 段増える | 制作が受け取ったかどうかを、企画が気にするか | 依頼したら「制作している」にする |
| R7 | 制作のページの HTML のエディタ | 制作が別の道具で作るなら、使われない | 制作が、どこで仕上げているか | HTML の書き出しだけにする |
| R8 | 制作を通さずに、配信のしくみに送る | 制作を通さない配信がないなら、要らない | 制作を通さない配信(アプリの通知だけ、など)があるか | 外す |
| R9 | 利用者が作るテンプレート(F25, F26) | 標準の 10 種で足りるなら、管理の手間だけが残る | 自分で作ったテンプレートが使われているか | 作る機能を管理者だけにする |
| R10 | テーマの種類の AI での分け(F83, F110) | 企画のときに種類を選ぶなら、後から分けなくてよい | 種類を、企画のときに選んでいるか | AI での分けを外す |
| R11 | 結果の「まとめて見る」(F80)と「比べる」(F82) | どちらも過去の配信と比べるもので、重なる | どちらを使っているか | 1 つにまとめる |
| R12 | 配信の対象(性別・年代。F109) | 対象を配信のしくみ側で決めているなら、CCP では要らない | 対象を、企画のときに決めているか | 外す(AI の前提からも外す) |
| R13 | 自分で依頼した配信を、自分で承認する | 承認の意味が薄れる | 承認を、別の人が行う決まりがあるか | 自分では承認できないようにする |

- 要検討の機能も、使ってみるまでは外さない。2〜4 週使ったあと、使った人に聞き、6 章の物差しと合わせて決める。
- 決めたことは、この表の「要らなければ」の列を「外した(日付)」「残す(理由)」に書き換える。

## 7. 機能ごとに前提にしていること

使ってみて、合わなければ直す。

| 機能 | 前提にしていること |
|---|---|
| 「あなた」 | 右上で選んだ人を、ログインしている人とみなす(本物のログインが入るまでの形)。ほかの画面では人を選ばない |
| 承認の依頼 | 配信カードごとに依頼する。相手は承認グループ(だれか 1 人が承認すれば、そのグループは済み)か、人 |
| 承認の決まり | 全員(指名したそれぞれから 1 人ずつ)/ 1 人(だれか 1 人)。既定は、すべての配信に同じ 1 つ |
| 自分の依頼 | 先に進めたいときは、自分で依頼した配信を自分で承認してよい |
| 差し戻し | 1 人でも差し戻したら、その依頼は止まる。理由を書く(やり取りにも残る) |
| 内容の変更 | 承認済みの配信の中身を変えて保存すると、承認待ちに戻り、依頼し直す |
| 週の確定 | 週の配信がそろったら、週ごとに確定する。確定した週の配信を変えるには、理由が要る |
| 制作への依頼 | 承認されたあとにだけ依頼する。承認の前に制作に相談したいときは、計画の配信カードのやり取りで、宛先に制作の人を入れる |
| 制作の写し | 制作のページの中身は、ある時点の配信カードの中身を固めた写し。承認されたときに下書きとして作り(企画が制作指示・担当・締め切りを整える)、「この内容で制作に依頼する」で固める。そのあと配信カードを変えても、制作のページは黙って変わらない(知らせて、新しい版を作る) |
| 依頼のあとの調整 | 承認のあとの文言・画像・商品・リンク先の調整は、企画と制作のあいだで決めてよい(承認のやり直しは要らない)。制作のページで直すと、配信カードは変わらず、制作の依頼の側に残り、「企画から変更」の印と元の値が出る |
| 制作の工程 | ① 制作に依頼する(企画)→ ② 受け取る(制作)→ ③ 制作する(制作)→ ④ 仕上がりの確認(企画)→ ⑤ 配信のしくみに送る(企画)。制作のページの題名の下に、この順で並び、いまの段のボタンだけが出る。承認されると、配信カードのプロセスのペインに「次: 制作に依頼する」が出る |
| 制作の人ができること | 読む・コピー・要素を直す・やり取り・タスク・「受け取った」・「制作が終わった」(できたもののリンクとひとことを添えられる) |
| 制作を通さないとき | 制作のページの「配信のしくみに送る」で、HTML・テキスト・リンク先を、配信のしくみに直接送る(いまは送り先の窓口だけ。返事は「送りました」) |
| やり取りのリアクション | 書き込みに、軽い返事(了解・見ています・対応します・ありがとう・確認したい)を付けられる。状態は変えない |

## 8. 使ってみて確かめたいこと

### 8.1 照らし合わせの進め方

<!-- hosted:begin -->
シートは、CCP の本番の画面の ⚙ →「前提運用の照らし合わせ」。上で聞き取り先を選ぶ(なければ名前を入れて「足す」)。段階のタブで絞れる。入力は、聞き取り先ごとに CCP の DB に保存される(表 `process_interviews`・`process_checks`)。ほかの人の入力は、開き直すか ⟳ で読み直すと見える。中の行は、3 章・5.3・6 章・7 章の写し(`src/hosted/processRows.ts`)なので、この文書の表を変えたら、そこも直す。

<!-- hosted:end -->
1. 段階ごとに、3 章と 7 章の「CCP の前提運用」を見せる(読み上げる)。
2. 今の運用を聞き、シートの「今の運用」に書く(だれが・何で・どのくらい)。
3. 「差なし / 差あり / 業務はない」を付ける。差ありなら「CCP に合わせる / CCP を直す / 保留」を、その場で利用先と決める(決められなければ保留)。
4. 5 章の要検討と、6 章の今の値も、同じ場で聞く。
5. 終わったら、シートの「Markdown で写す」を 3.8 に貼る。

段階ごとに聞くことの例:

| 業務 | 聞くこと |
|---|---|
| A1 | 配信の予定・進み具合を、どこで持っているか(表計算・予定表・ほか)。国・チャネル・部署で分かれているか |
| A2〜A7 | 1 本の配信の企画に、どのくらいかかるか。いちばん時間がかかるのはどこか(テーマ・画像・文言・商品・制作指示)。商品・画像を選ぶとき、何を見ているか |
| A8 | 制作の前に、受け取った人にどう見えるかを確かめているか |
| B1〜B3 | 週のレビューは、会議か、資料を回すか。資料はだれが、どのくらいかけて作るか。意見と、直したかどうかを、どこで追っているか |
| B4〜B5 | 承認は、だれが・何で(メール・チャット・会議)行っているか。週で締めているか、配信ごとか。決まったあとの変更は、どう伝えているか |
| C1〜C4 | 制作への依頼は、何で(指示書のファイル・メール・チャット)送っているか。制作は、どこで仕上げているか。仕上がりは、何で確かめているか |
| C5 | 配信のしくみに入れるのは、だれか。制作を通さない配信はあるか |
| D1〜D3 | 在庫切れ・方針や日程の変更で、差し替え・取りやめたことが、どのくらいあるか。いつ・どうやって気づいたか |
| E1〜E3 | 結果の数字は、だれが・どこに集めているか。振り返りの会はあるか。学びを、次の企画でどう使っているか |
| G1〜G2 | US と JP で、進め方・資料は違うか |
| P(7 章) | 決まりを 1 つずつ読み上げ、今の進め方と同じかを聞く |
| 全体 | CCP を使い始めたら、やめる資料・やり取りはどれか(4 章の「二重になる」) |

### 8.2 前提の流れ(7 章)

- 承認の段階(起案 → 承認待ち → 承認済み)と、週の確定の 2 つで、足りるか・多すぎないか(5 章の R1)。
- 承認グループと「全員 / 1 人」の決まりで、実際の承認の進め方に合うか。
- 制作に依頼するのは承認のあと、という順で困らないか(承認の前に制作に見せたい場面がどのくらいあるか)。
- 制作の人が、制作のページだけを見て作れるか(足りない情報・コピーしにくいものは何か)。
- 依頼のあとに直した内容を、配信カード(企画)にも戻したいことがあるか(いまは戻さない)。どこまで直してよいか(承認のやり直しが要る変更はあるか)。
- 写しを固める時点(依頼したとき)でよいか。依頼のあとに企画が変わったとき、どう知らせてほしいか。
- 「受け取った」「制作が終わった」のほかに、制作の人が押したい返事はあるか(「受け取った」自体が要るかは 5 章の R6)。
- HTML のソースは、どこで・どう使うか(配信のしくみに入れるか、制作の出発点にするか。5 章の R7)。
