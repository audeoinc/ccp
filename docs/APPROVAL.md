# ユーザーと承認の設計(2026-10-17 に利用者と決めた)

GitHub のプルリクエストのように、配信カードごとに「承認を依頼」し、指名した承認グループ・人が承認する仕組み。
作る順番は [BACKLOG.md](BACKLOG.md) の 11 章(U1〜)。いまの承認(W9。だれでも押せる、名前は自由入力)は、U4 ができるまで残す。

## 1. なぜ変えるか(利用者の指摘)

- 段階が多くて分かりにくい(配信の 未起案 / 検討中 / 承認済み / 確定 と、週の 下書き / レビュー中 / 確定)。
- 配信カード 1 本だけを承認に回す仕組みがない(承認待ちになるのは、週の「レビューに出す」だけ)。
- だれが承認者なのか、その人たちが承認したのかが分からない。

## 2. 決めたこと

| 項目 | 決めたこと |
|---|---|
| 前提 | 最終的には、ログインがあり、ユーザーが登録されている。**ログインより先に、ユーザーマスタを作る**(ログインが入ったら、ログインしたメールアドレスで `users` の行を引くだけにする) |
| 依頼の相手 | **承認グループ**(だれか 1 人が承認すれば、そのグループは済み。休みの人がいても止まらない)。人を直接指名してもよい |
| 決まり | **全員**(指名したグループ・人の、それぞれから 1 人ずつ)/ **1 人**(指名した中のだれか 1 人)。種別(販促 / CRM / EC)ごとに既定を持ち、依頼のときに変えられる |
| 自分の依頼 | **自分で依頼した配信は、自分では承認できない**(自分のグループの承認者にも数えない) |
| 差し戻し | **1 人でも差し戻したら止める**(決まりが「1 人」でも。だれかが止めたものが、ほかの人の承認で通らないように) |
| 2 つのグループに入っている人 | **1 回の承認は、1 グループ分だけ**(「全員」の意味 = 別々の目で見る、を保つ) |
| ユーザー・グループの編集 | **ログインが入るまでは、だれでも画面で編集できる。変更はすべて履歴に残す**(ログインがない間は、「あなた」を選ぶ時点でほかの人を選べるので、編集だけを固くしても守れる範囲は増えない)。ユーザーに「管理者」の印を最初から持たせ、ログインが入ったら、編集を管理者だけにする |
| 通知 | **メールが飛ぶ前提で作る**。承認の操作のたびに、送る箱(`notifications`)に行を積む。実際に送る仕組みは、いまは作らない(Workbench は外につながらないので、送らない設定でも困らない作りにする)。同じ箱を、画面の「自分宛ての依頼」にも使う |
| 承認済みの内容を変えたとき | いまと同じく、承認をやり直す。依頼は「古くなった」として残し、新しい依頼を出し直す(1 回目にだれが承認したかも残る) |
| 見せ方 | 配信は 未起案 / 承認待ち / 承認済み(週が確定したら鍵マーク)。週は 確定前 / 確定。データの値(`confirmed`・週の `review`)は変えない |

## 3. データ

| 表 | 列 | 中身 |
|---|---|---|
| `users`(U1) | `name`・`email`・`role`(`member` / `admin`)・`status`(`active` / `inactive`) | だれがいるか。**メールアドレスが、本人を見分けるかぎ**(ログイン・通知の宛先)。消さずに `inactive` にする(履歴に名前が残るように) |
| `approval_groups`(U1) | `name`・`description`・`status` | 承認グループ(MD・ブランド・法務 など)。配信の種別とは分けて持つ(どの部署の配信か と、だれが承認するか は別のため) |
| `approval_group_members`(U1) | `approval_group_id`・`user_id` | だれがどのグループにいるか(1 人が複数のグループに入ってよい) |
| `approval_rules`(U3) | `department`・`rule`(`all` / `any`)・`group_ids`・`user_ids`(id の配列の JSON) | 種別ごとの既定の承認者と決まり(1 種別に 1 行)。⚙ →「ユーザーと承認グループ」→「承認の決まり」 |
| `approval_requests`(U3) | `delivery_card_id`・`card_name`・`requested_by`(ユーザーの id)・`requested_by_name`・`rule`・`status`(`open` / `approved` / `changes_requested` / `stale` / `withdrawn`)・`requested_at`・`closed_at`・`note` | 依頼 1 回分。内容を変える・出し直す・取り下げると、生きている依頼(`open` / `approved` / `changes_requested`)は `stale` になる |
| `approval_reviewers`(U3) | `approval_request_id`・`approval_group_id` または `user_id`・`reviewer_name`・`decision`(`pending` / `approved` / `changes_requested`)・`decided_by`(ユーザーの id)・`decided_by_name`・`decided_at`・`note` | 依頼の相手ごとの状態。グループのときは、だれが済ませたかを `decided_by` に残す。名前は、その時のものを残す(消しても読めるように) |
| `notifications`(U5) | `user_id`・`email`・`kind`(`review_requested` / `approved` / `changes_requested` / `withdrawn`)・`subject`・`body`・`delivery_card_id`・`approval_request_id`・`status`(`pending` / `sent` / `skipped`)・`sent_at` | 送る箱。承認の操作のたびに、サーバー(`approvals.py` の `_notify`)が宛先ごとに 1 行積む(操作した本人には積まない。グループ宛ては、メンバー全員)。宛先のメールアドレスは、積んだ時点のものを残す。送る仕組みは U8 |

- 「誰が」の記録(`events.actor`・コメントの書いた人・`x-ccp-actor`)は、これまでどおり名前の文字で残す。U2 から、その名前は、ユーザーマスタから選んだ人の名前になる(ブラウザに `me.user`(ユーザーの id)と `me.name` を覚える)。ユーザーが 1 人も登録されていない環境では、これまでどおり名前を入れられる(いまの運用を止めないため)。
- ユーザー・グループの変更は、操作の履歴(`events`)に、種類 `user_change` / `group_change` で残す(だれが・いつ・何を)。

## 4. 承認の操作は、サーバーで行う(U4。`server/ccp/approvals.py`、画面は `src/data/approvals.ts`・`src/ApprovalBar.tsx`)

承認の依頼・承認・差し戻し・取り下げは、表を画面から直接書かずに、サーバーの窓口で行う。

| 窓口 | すること |
|---|---|
| `POST /api/approvals/requests` | 依頼する。相手(グループ・人)の名前を写し、生きている依頼を `stale` にし、配信を `reviewing` に、履歴に `request` |
| `POST /api/approvals/requests/{id}/decide` | 承認(`approved`)/ 差し戻し(`changes_requested`。理由は必須)。本人が決められる相手の行(本人の指名 → グループの順)を 1 つだけ更新し、決まりを判定。そろえば依頼と配信を `approved`、差し戻しなら依頼を `changes_requested` にして理由をコメントにも残す。履歴に `approve` / `reject` |
| `POST /api/approvals/requests/{id}/withdraw` | 依頼した人が取り下げる。配信が `reviewing` なら `not_started` に戻す。履歴に `withdraw` |
| `POST /api/approvals/reset` | 内容が変わった(承認後・確定後の変更)ので、生きている依頼を `stale` にする(配信カードの保存から呼ぶ。配信のステータスと履歴は、保存の側で書く) |

- 「あなた」は、画面が `actor: {id, name}` で送る(ログインがないので、いまは信じる。ログインが入ったら、ここだけを直す)。
- 判定(`request_outcome`・`eligible_reviewers`)は、画面の `src/approvals.ts` と同じ。例 `server/tests/approval_cases.json` を、Python(`test_approvals.py`)と Node(`scripts/check-approvals.mjs`。`npm run verify` に含む)の両方で確かめる。
- 撮影・デモ用のビルドは、`src/mock/approvals.ts` が同じ流れをメモリ上で行う(`vite.mock.config.ts` が差し替える)。

- 「承認できるのは指名された本人だけ」の確認は、ログインが入ったら、サーバーでしか守れない。今のうちに窓口を分けておけば、そのとき 1 か所を直すだけで済む。
- 承認・決まりの判定・配信のステータスの更新・通知を積む、までを 1 つのトランザクションで行う(承認したのに通知が残らない、を防ぐ)。
- 配信の `status` の列は、これまでどおり書く(依頼中 = `reviewing`、決まりを満たした = `approved`)。カレンダー・確認の一覧・アラートが、今のまま動く。
- 撮影・デモ用のビルドは、同じ判定を `src/mock` で行う(判定の関数は、画面とサーバーで同じ結果になるよう、テストで突き合わせる)。

## 5. 画面

- ⚙ →「ユーザーと承認グループ」(U1): ユーザーの一覧(追加・編集・無効にする)、承認グループ(メンバーの出し入れ)、変更の履歴。
- 「あなた」(U2): 週の帯・配信カードの下・コメントの名前の欄を、ユーザーから選ぶ形にする。
- 配信カード(U4): 下のボタンの行の上の「承認」の帯(`ApprovalBar`)。依頼がなければ「承認を依頼」(相手と決まりを選ぶ。既定は種別ごと)。依頼中は、相手ごとの状態(「MD ✓ Aya Mori 10/13 ・ Brand 未定」)と、承認者には「承認」「差し戻す」、依頼した人には「取り下げ」。内容を変えていると、先に保存してもらう。以前の「保存して承認」「差し戻す」は、これに置き換えた(週の帯の「まとめて承認」は U6 まで残る。依頼を見ずに承認済みにするので、U6 で置き換える)。
- 自分宛ての依頼(U5): ヘッダーの「依頼」(`InboxButton`)に件数。押すと、自分(と自分のグループ)宛ての、依頼中の依頼の一覧(押すと配信カードが開く)。**送る箱ではなく、依頼中の依頼から計算する**(`useApprovalInbox`。箱の行は写しで、だれかが済ませたあとも残るため)。だれかが済ませた分は、自然に消える。
- 週の帯(U6): 「レビューに出す」「下書きに戻す」「まとめて承認」をやめ、「まとめて依頼(N)」(未承認で依頼のない配信を、種別ごとの既定の相手に依頼。既定がない種別は飛ばして知らせる)と「自分宛てを承認(M)」(配信カードと同じ窓口を順に呼ぶ。`src/weekApprovals.ts`)に置き換えた。週の状態は 確定前 / 確定 の 2 つ(データの `draft` / `review` は、どちらも確定前)。「週を確定」は、承認されていない配信があれば件数を出して確かめる。
- 配信の見せ方(U6): 画面のステータスは 未起案 / 承認待ち / 承認済み の 3 つ(`src/status.ts` の `statusOptions`・`statusView`・`statusLabel`)。確定した週の配信は「承認済み」+ 鍵マーク(`LockMark`)。履歴だけ「承認済み(週が確定)」と読み分ける。データの値(`confirmed`)は変えていない。

## 6. ログイン(U7。下地は 2026-10-17 にできた。IAP を有効にするのは、人の GCP の操作)

- **仕組み**: ログインそのものは、Cloud Run の前に置く IAP(Identity-Aware Proxy)が行う。サーバー(`server/ccp/identity.py`)は、IAP が付ける見出し `X-Goog-IAP-JWT-Assertion` を Google の公開鍵で検証して、メールアドレスを取り出す(環境変数 `CCP_IAP_AUDIENCE` に IAP の宛先を設定したときだけ。検証なしの `X-Goog-Authenticated-User-Email` は信じない)。手元では `CCP_DEV_USER_EMAIL` で、その人がログインしたことにできる。どちらもなければ「ログインなし」= これまでどおり、画面で「あなた」を選ぶ。
- **メールアドレスが、本人を見分けるかぎ**(`users.email`。大文字小文字は区別しない)。`GET /api/me` が、ログインしている人と、それに当たるユーザーを返す。
- **ログインしているときの動き**: 「あなた」はその人に固定(`MePicker` は名前だけ出す。登録のないメールアドレスは、その旨を出す)。承認の依頼・承認・差し戻し・取り下げは、画面が送った「あなた」を見ず、ログインした人で行う(`approvals.py` の `_actor`。登録がなければ 400)。ユーザー・承認グループ・メンバー・承認の決まりの書き込みは、管理者(`users.role` = `admin`)だけ(`data_api.py` が `people_edit_denied` で 403。画面は見るだけになる)。
- **ログインがないときの動き**: これまでどおり(だれでも「あなた」を選べる・だれでも編集できる・変更は履歴に残る)。
- **人が行うこと(GCP)**: ロードバランサ + IAP を Cloud Run の前に置き、OAuth の同意画面・許可するユーザー(Google アカウント)を設定し、Cloud Run への直接のアクセス(`run.app` の URL)を塞ぐ(ingress を内部とロードバランサだけに)。そのうえで Cloud Run の環境変数 `CCP_IAP_AUDIENCE`(`/projects/<番号>/global/backendServices/<ID>`)を設定する。Basic 認証(`APP_PASSWORD`)は、IAP が入れば外してよい。Workbench は Jupyter の中継を通すので、IAP は使えない(ログインなしの運用のまま。または Workbench の `CCP_DEV_USER_EMAIL` で 1 人に固定)。
