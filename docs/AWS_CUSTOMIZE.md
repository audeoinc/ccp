# AWS 側で CCP を調整しながら、新しい版を取り込む

AWS の環境で作業する人と Claude のための決まりと手順です(2026-11-04 利用者と決めた)。**更新・スキーマの変更・画面の変更の前に、この文書を読んでください。**

## 1. 考え方

- **ねらい:** 利用先の BigQuery で取得できるデータを最大限に使い、CCP から生まれる成果を最大にする。
- **データと、それに伴う設定項目は、AWS 側で独自に開発する。** PostgreSQL の内容は、共通の表も含めて、すべて変わりうる。
- **UI・UX・機能は、開発側の版から取り込む。** ZIP の作り方は変わらない。変えるのは、入れ方(総入れ替え → マージ)。
- **マージは、ZIP を AWS 側の Claude に渡して任せる。** 利用者が細かい指示をしなくても進むように、5 章の手順で行い、ぶつかりも解消する。

| 部分 | 例 | 持ち主 | 版を取り込むとき |
|---|---|---|---|
| データ・それに伴う設定項目 | PostgreSQL の表と列、取り込み、選択肢 | AWS 側 | AWS 側の形を残す |
| UI・UX・機能 | 画面・操作・新機能 | 開発側 | 取り込み、AWS 側のデータの形に合わせる |
| サーバーの置き方 | 認証・AI の出口・ファイルの置き場所 | 開発側 | そのまま取り込む |

- **新機能がデータをどう読むかは、AWS 側の Claude が版ごとに合わせる。** 読み口を挟む仕組みは、先回りして作らない。
- **ぶつかりが増えたら、利用者に伝える。** 利用者を通して開発側に伝わり、開発側がその所を減らす(8 章)。
- **開発側の新機能は、空の値・知らない値で落ちない**ように作られる。AWS 側の列の値が開発側の想定と違っても、まず動く。

## 2. 調整のしかた

データに合う形を優先して決める。**下の表は禁止の順番ではなく、マージの手間の目安。** 手間が同じなら、上を選ぶ。

| 調整のしかた | 例 | マージの手間 |
|---|---|---|
| BigQuery のビューで整える | 値の整形・`page_url` を組み立てる | なし |
| CCP の画面の設定で変える | 店の URL の形・表の場所・AI | なし |
| 別のファイルで足す・重ねる | 列・表・選択肢・画面・処理(3 章・4 章) | ほぼなし |
| 共通のファイルを直す | 列の名前の変更・共通の画面や処理の変更 | ぶつかることがある。AWS 側の Claude が解消する |

- **サーバーの置き方の違い**は、ここで直さず、開発側に伝える(差し込み口とアダプターで吸収する。[ARCHITECTURE.md](ARCHITECTURE.md) の 0.5 章)。
- **`products` の列の名前を変える**ことはできる。ただし多くのファイル(画面側だけで、`products` の型を使うものが約 85)に影響するので、データに合わせる効果と比べて決める。
- **`products` を読む機能をそのまま使いたいとき**は、細かい形を AWS 側の表に持ち、`products` には機能が使う単位で行を入れる方法もある。
- **商品の単位そのものが変わる**ときも、AWS 側で決めてよい。作り変える範囲が大きいので、作る前に利用者に伝える。

## 3. AWS 側のファイルの置き場所

次のフォルダは AWS 側だけのもの。**開発側はここにファイルを作らない**ので、マージでぶつからない。

| 置き場所 | 置くもの |
|---|---|
| `src/client/` | 足す画面・差し替える画面。足した列・表の型は `src/client/models/`(4 章) |
| `server/ccp/client/` | 足すサーバーの処理。足す列・表は `server/ccp/client/schema.json`(4 章) |
| `docs/client/` | この環境の記録(下の 2 つなど) |

- 共通のファイルには、呼び出しの登録など、**要る行だけ**を足す。
- `docs/client/CHANGES.md` に、次を書く。次の版を取り込むときの手がかりになる。
  - 共通のファイルを直した所(ファイル・列の名前・理由)
  - 差し替えた画面(元の画面・差し替え先・理由)。ここに載っている画面には、開発側の改善が届かない
- `docs/client/DATA_MAP.md` に、BigQuery の表と CCP の表・列の対応を書く(6 章)。
- AWS 側の Git だけにあるので、相手の表や列の名前を書いてよい。**パスワード・鍵・トークンは書かない。**
- このリポジトリの `CLAUDE.md`・`README.md` などの届いたファイルは、版が来るとぶつかりやすい。この環境の決まりは `docs/client/` か、リポジトリの最上位の `CLAUDE.md` に書く。

## 4. スキーマの変え方

**スキーマの変更は、できるだけ `server/ccp/client/schema.json` に書く。** サーバーは `server/schema.json` と重ねて読み、起動のときに DB に反映する(DB の列は消さない)。開発側が `schema.json` を変えても、このファイルとはぶつからない。**DB を手で変えない**(定義に戻されるか、起動のときに失敗する)。

**止まるのは、サーバーが動けないときだけ。** それ以外は通して、注意と次にやることを出す。

```json
{
  "tables": {
    "products": { "columns": [["maker_code", "text", { "index": true }], ["size_band", "choice"]] },
    "maker_notes": {
      "columns": [["body", "text"]],
      "lookups": [["product_id", "products", { "onDelete": "CASCADE" }]],
      "unique": [["product_id"]]
    }
  },
  "choices": { "products.size_band": ["s", "m", "l"] }
}
```

| したいこと | 書く場所 |
|---|---|
| 列・参照・表を足す | 重ねるファイル |
| 足した `choice` の列の選択肢、足した列をやめる(`retired`) | 重ねるファイル |
| 共通の列の型・指定・`retired`・`choices` を変える | 重ねるファイル(7 章の行が残っていれば、まだ版に入っていない) |
| 共通の列の名前を変える | `server/schema.json` を直す。ぶつかれば AWS 側の Claude が解消する |

- **止まるのは次の 4 つ**(`npm run verify`・起動・`check` が、理由と直し方を出す): ファイルが読めない、知らない型、SQL に入れられない名前、共通の表の `unique`(一意にするときに、重なった行が消えるため)。
- **型を変えると、起動のときに DB の列も変える。** 今ある値を新しい型に変換できないと、起動に失敗する。先に DB の写しで試す。
- 開発側の新しい版に、同じ定義の列が入ったら、そのまま動く。⚙ の「設定の状態」と `check` が、消してよい行を教える。
- 型は、共通のファイルを直さず、`src/client/models/<表の名前>.ts`(例: `makerNotes.ts`)に `export interface` で書く。足した `choice` の列は、共通の型と同じ形の `export const …SizeBand = { s: '…' } as const` も書く。`npm run verify` が、重ねたあとの定義と型を突き合わせる。
- 共通の定義を変えたら、`docs/client/CHANGES.md` に名前(例: `products.season`)と理由を書く。書いていなければ、`npm run verify` が注意を出す(止めない。届いたままの定義 `server/schema.base.json` と比べる。このファイルは版と一緒に届くので、手で直さない)。

## 5. 新しい版を取り込む

**利用者が ZIP を AWS 側の Claude に渡したら、Claude がこの章のとおりに進める。** `main` への push とサーバーへの反映の前には、利用者に結果を伝える。

Git のブランチを 2 本持つ。

```
vendor : ZIP の中身だけ(手で直さない)  ── v1 ── v2 ── v3
                                          \     \     \
main   : 実際に動かす(AWS 側の調整が載る) ─ 調整 ─ merge ─ merge ─ merge
```

- 別のリポジトリは作らない。同じリポジトリのブランチで足りる。
- 作業は、**サーバーとは別の作業コピー**で行う。サーバーは `main` を取得するだけ(`scripts/workbench.sh update` は `git pull --ff-only` なので、サーバーの上でコミットすると止まる)。
- **版が届くたびに、間をあけずに取り込む。** あけるほど、ぶつかる量が増える。

### 5.1 最初の 1 回

ZIP を入れたままのコミット(手で直す前のもの)から、`vendor` を作る。

```bash
git switch -c vendor <ZIP を入れたままのコミット>
git push -u origin vendor
```

**そのようなコミットがないとき**(ZIP の取り込みと手の直しが、同じコミットに入っている)は、始めずに利用者に伝える。そのまま進めて ZIP を入れ直すと、次のマージで AWS 側の直しが消えることがある。

### 5.2 版が届くたび

**最初に、差分の一覧を見る**(何がぶつかりうるかが、マージの前に分かる)。`ccp/` の中で、`main` にいる状態で実行する。

```bash
npm run client:diff
```

「足した所」と「共通のコードを変えた所」に分けて出る。「CHANGES.md にありません」と出たファイルは、先に `docs/client/CHANGES.md` に書く。

```bash
VER=<版>
git switch vendor
git pull

# ccp/ の中だけを入れ替える(前の版にあって、新しい版にないファイルを残さないため)
find ccp -mindepth 1 -maxdepth 1 -exec rm -rf {} +
TMP=$(mktemp -d)
unzip -q ~/ccp-aws-$VER.zip -d "$TMP"
cp -a "$TMP/ccp-aws-$VER/." ccp/
rm -rf "$TMP"

git add -A ccp
git commit -m "CCP AWS 版 $VER"
git tag "aws-$VER"
git push origin vendor --tags

git switch main
git pull
git merge vendor          # ぶつかれば、5.4
```

- **`vendor` で `ccp/` の外を消さない。** 消すと、マージで `main` からも消える。
- **`vendor` で手を入れない。** ZIP の中身だけにする。
- 上の `find` は、Git の外のファイル(`server/workbench.env`・写真など)も消す。**サーバーの上の作業コピーで実行しない。**

### 5.3 マージのあとの確認(push の前)

```bash
cd ccp
npm ci
npm run verify
(cd server && .venv/bin/python -m unittest discover tests)
```

- 作業コピーに `server/.venv` がなければ、先に `scripts/workbench.sh setup` を実行する。
- 通らなければ、`main` に push しない。AWS 側の調整と新しい版の組み合わせは、開発側では確認できない。**ここが、その唯一の確認。**
- データの形を変えたために共通のテストが通らないときは、テストや処理を AWS 側の形に合わせ、`docs/client/CHANGES.md` に書く。
- **新しい版の新機能を、AWS 側のデータの形に合わせる。** 新機能が読む列が AWS 側で変わっていれば直し、画面で動きを確認する。
- 新しい版の新機能を、`docs/client/CHANGES.md` の差し替えた画面と見比べる。必要な分を、差し替えた画面にも取り込む。
- 通ったら、結果を利用者に伝えて `git push origin main`。サーバーへの反映は、人の指示で行う。

```bash
scripts/workbench.sh update
scripts/workbench.sh check    # 足りない設定があれば、ここで出る
```

### 5.4 ぶつかったとき

- 両方で足した行なら、両方を残す(`schema.json` の列など)。
- **データ・設定項目がぶつかったら、AWS 側の形を残す。** そのうえで、開発側の機能が動くように合わせる。
- **UI・UX・機能がぶつかったら、開発側の変更を取り込む。** AWS 側の直しが要らなくなれば、やめて `docs/client/CHANGES.md` の行を消す。
- 判断できないときは、利用者に聞く。
- **同じ所が版のたびにぶつかるなら、利用者に伝える**(8 章)。

### 5.5 差分を見る

```bash
git diff vendor main --stat -- ccp/
git diff vendor main -- ccp/
```

`ccp/` を指定する(外のフォルダの違いを混ぜないため)。`docs/client/CHANGES.md` にない共通のコードの差分があれば、書き足す。

### 5.6 前の版に戻す

`main` のマージのコミットを取り消す。

```bash
git revert -m 1 <マージのコミット>
```

## 6. 最初に行うこと

大きく作り変える前に、`docs/client/DATA_MAP.md` に、次をまとめる。**どれくらい作り変えが要るかを、推測せずに判断するため。**

1. BigQuery にある表と列(形だけ。実際の値は書かない)
2. CCP の表・列のどれに対応するか
3. CCP で使っていないが、成果につながりそうなデータ
4. CCP の表・列のうち、変える・やめる候補
5. 差し替えたい画面の候補

まとめたら、利用者に見てもらい、AWS 側で進め方を決める(開発側には渡さない。8 章)。

## 7. 開発側で作るもの

スキーマの重ね読み(列・表を足す。4 章)、書き漏れの注意(4 章)、差分の一覧(5.2)は、できた。次の行は、まだ版に入っていない。できたら行を消して版で届ける。**版を取り込んだら、この章を見直す。**

| 作るもの | 中身 | 入るまでのやり方 |
|---|---|---|
| 重ねるファイルで共通の列を変える | 型・指定・`retired`・`choices` | `server/schema.json` を直す |
| 画面を差し替える仕組み | 実際に必要になってから作る | 呼び出しの行を直して `CHANGES.md` に書く |

## 8. 開発側へ伝える

**AWS 側の情報は、開発側に持ち出せない。** 開発側は、この環境のデータも、`docs/client/` の中身も、マージの結果も見られない。

- **どの画面を差し替えるか、どう作り変えるかは、AWS 側で利用者と決める。** 開発側の判断を待たない。
- **マージのぶつかりや、確認が通らないときも、AWS 側で解消する。**
- 開発側に頼みたいことは、利用者に伝える。**利用者が、一般的な機能の要望として開発側に話す**(例: 「商品に階層を持てるようにしたい」)。相手の名前・表や列の名前・実際の値・ログの中身は含めない。
- **ぶつかりが増えたら、同じ形で伝える**(例: 「商品の画面と列の定義が、版のたびにぶつかる」)。開発側が、その所を減らす。先回りはせず、必要になった所から直す。
- **汎用的な改善**も同じ形で伝える。開発側が取り込めば、次の版のマージのあと、差分から消える。
- **`docs/client/` の中身を、そのまま渡さない。**
