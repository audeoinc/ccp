# 設計メモ: Workbench の開発用の画面(BigQuery の出力の SQL・ポリシーの文書を、Gemini と作る)

利用先の Workbench の中で、**CCP が読むデータを用意する作業**を、Gemini と一緒に進めるための画面です。CCP とは入り口も URL も別にします。使うのは開発する人だけ(配信の担当者は使わない)。

- 状態: 案(2026-10-22。利用者と方向を決めた。まだ作っていない。バックログ B10)
- 関係する文書: 出力の形 [BIGQUERY_EXPORT.md](BIGQUERY_EXPORT.md)、変換の手引き [BIGQUERY_CONVERT.md](BIGQUERY_CONVERT.md)、ポリシーのファイルの形 [POLICY_FORMAT.md](POLICY_FORMAT.md)
- 利用先のプロジェクト・データセット・テーブル・文書の名前は、この文書にもコードにも書かない

---

## 1. 前提(利用者に確かめたこと。2026-10-22)

| 前提 | 内容 |
|---|---|
| データの置き場所 | CCP で使うデータのほぼすべてが、利用先の BigQuery と GCS にある。本物のデータには、**Workbench からしか届かない** |
| Claude | 利用先の環境の Claude は、Workbench に入れない。`bq query` も使えない(BigQuery に問い合わせを投げられない)。Claude ができるのは、コンフルを読んでデータの仕様をまとめるところまで |
| Gemini | Workbench からは使える(CCP の `/api/ask` と同じ、Vertex AI の Gemini) |
| 問い合わせを投げられるもの | **Workbench で動く CCP のサーバー**(Python の BigQuery のライブラリ。`server/ccp/bq.py` と同じ認証)だけ。だから、この画面が、BigQuery の試しと答え合わせの唯一の場所になる |
| 使う人 | 開発する人 1 人(利用者本人)。作り込みより、**SQL をコピーして持ち出しやすいこと**を優先する |
| BigQuery の出力 | ビューではなく**表**にして、定期的に更新する(読む時間を短くするため)。表を作る SQL(DDL)は、画面が作り、**実行は人が BigQuery のコンソールで行う** |
| GCS の文書 | マーケティングポリシー・文言のルールが、文書やスプレッドシートでまとまっている。これを CCP のポリシーの形([POLICY_FORMAT.md](POLICY_FORMAT.md))に直して取り込む |

## 2. 方針(結論)

1. **URL は `/dev/`、API は `/api/dev/*`。** CCP の画面(`/`)とは、つなげない(CCP の画面から入る道を置かない)。サーバーは同じ(同じプロセス、同じ設定)。
2. **既定では無効。** 環境変数 `CCP_DEVTOOLS=1` のときだけ、画面と API を出す(無効のときは 404)。CCP のパスワード(`APP_PASSWORD`)を使っているなら、同じように守る。
3. **BigQuery と GCS は、読むだけ。** BigQuery には SELECT だけを、行数と読む量の上限を付けて投げる。表を作る・消すことは、画面からはしない。書き込むのは、CCP の DB のポリシー(既存の取り込み)と、Workbench のフォルダの中の作業ファイルだけ。
4. **答え合わせは、CCP の取り込みと同じ関数を使う。** BigQuery の出力は `bq_validate`(`bq-check` と同じ)、ポリシーは `policies` の読み分け(`/api/policies/preview` と同じ)。「画面では通ったのに、取り込めない」を起こさない。
5. **Gemini に渡す「前提」は、画面が組み立てる。** 出力の形・方針(表にする など)・手本の SQL・本物の列の一覧・コンフルのまとめを、毎回同じ順で渡す。会話のたびに口で説明しなくてよいように。
6. **作ったものは、Workbench のフォルダに保存する**(`server/devwork/`。Git に入れない)。利用先の表の名前を含むので、リポジトリには戻さない。DB に置かないのは、`import-pack --yes` で DB をまるごと置き換えても消えないようにするため。
7. **Gemini が書いたプログラムは、実行しない**(最初の版では)。文書の加工は、Gemini に直接書き直させる(3.2)。

## 3. 画面の流れ

画面は 1 枚で、上のタブで 2 つの作業を切り替える。左に「作業の一覧」、右に「いまの作業」。

### 3.1 タブ「BigQuery の出力」

6 つの出力(SPU・SKU・SKU の在庫・週ごとの実績・天気予報・販売順位)ごとに、次の段を上から順に進める。進める順は [BIGQUERY_CONVERT.md](BIGQUERY_CONVERT.md) の 3 章と同じ(SPU → SKU → 在庫 → 週ごと → 天気予報 → 順位。SKU は SPU に、在庫は SKU に結びつくかを確かめるため)。

| 段 | すること | 画面 |
|---|---|---|
| ① 元の表を選ぶ | 元のデータセットを入れると、`INFORMATION_SCHEMA` から表と列(名前・型・説明)の一覧を取る。使う表に印を付ける | 表の一覧(検索できる)。表を開くと、列の一覧と、先頭の数行(`LIMIT 20`) |
| ② 仕様のまとめを入れる | 利用先の Claude がコンフルからまとめた Markdown を貼るか、ファイルで入れる。出力ごとに分けても、1 つにまとめてもよい | 大きめの入力欄。保存すると、ほかの出力でも使える |
| ③ 前提を確かめる | 画面が、Gemini に渡す前提を組み立てて見せる(4 章) | 前提の全文(読むだけ)と、長さ(文字数)。「前提をコピー」 |
| ④ SQL の案を作る | Gemini が SELECT を書く。理由と、決めきれなかったこと(どの列を `category` にしたか など)も返させる | SQL(色付き・行番号)、理由、気になる点 |
| ⑤ 試しに流す | まず dry-run(料金なし)で、読む量と、文の種類が SELECT かを見る。通れば、行数を絞って流す | 読む量(GB)、かかった時間、結果の表(先頭 200 行) |
| ⑥ 答え合わせ | 結果を `bq_validate` に通す。キーの重複・必須の空・市場の値・数値の範囲・結びつき(SKU → SPU など)。NG と注意を出す | `[NG]` / `[注意]` の一覧。「NG を Gemini に返して直す」で ④ に戻る |
| ⑦ 表を作る SQL を出す | 合格した SELECT を、`CREATE OR REPLACE TABLE <出す先> AS …` にして出す。スケジュールされたクエリに貼る形(下の 3.3) | SQL と「コピー」。**実行は人がコンソールで** |
| ⑧ CCP の設定 | 出す先の表の場所を、`server/workbench.env` に書く行(`BQ_SPU=…`)にして出す。表なので `BQ_<名前>_WATCH` は要らない | 設定の行と「コピー」 |

⑤ の「試しに流す」は、本物の行を全部は読まない。答え合わせ(⑥)は、全件で確かめないと見つからない NG(キーの重複 など)があるので、「全件で確かめる」を別のボタンにする(読む量を見せてから、人が押す)。

**版を残す。** ④ で作るたびに、SQL を新しい版として保存する(v1, v2, …)。版ごとに、試した結果と答え合わせの結果を一緒に残す。2 つの版の違い(差分)を見られるようにする。いちばん新しい合格の版に「採用」の印を付ける。

### 3.2 タブ「ポリシーの文書」

| 段 | すること | 画面 |
|---|---|---|
| ① ファイルを選ぶ | GCS のバケットとフォルダを入れると、ファイルの一覧を出す(名前・大きさ・更新日時) | ファイルの一覧。複数選べる |
| ② 文字にする | 選んだファイルの中身を、Gemini に渡せる形にする(5 章) | 文字にした中身(読むだけ)。読めなかったファイルと理由 |
| ③ 書き直す | Gemini が、[POLICY_FORMAT.md](POLICY_FORMAT.md) の形(ルール系は Markdown、販売系は CSV)に書き直す。元の文書のどこから取ったかを、決まりごとに書かせる | 書き直した結果(編集できる)。元の文書と並べて見られる |
| ④ 確かめる | 既存の読み分け(`/api/policies/preview` と同じ)に通す。読めた件数、読めなかった決まり・行と理由 | 結果の一覧。「読めなかった分を Gemini に返して直す」で ③ に戻る |
| ⑤ 取り込む | 合格したら、既存の取り込み(`/api/policies/import`)で CCP に入れる。ファイル名は、元の文書の名前から作る(同じ名前で取り込み直すと入れ替わる) | 確かめの画面を出してから、取り込む |

同じ文書を毎週のように加工し直すことが分かったら、そのときに「加工のスクリプトを Gemini に書かせて保存し、使い回す」形を考える(7 章)。

### 3.3 表にして、定期的に更新する(Gemini に渡す方針)

利用者の方針(2026-10-22): 出力は表にし、定期的に更新して、CCP が読む時間を短くする。これを、Gemini に渡す前提に**決まりとして**書く(4 章の「出力の方針」)。

- 出力は、`CREATE OR REPLACE TABLE <出す先> AS SELECT …` で作る。ビューにしない。
- 何度流しても、同じ結果になる書き方にする(途中で止まっても、流し直せば済む)。
- `as_of` には、**元のデータの時点**を入れる(更新した時刻・`CURRENT_TIMESTAMP()` ではない。仕様の 1 章)。
- 読む量を抑える(元の表がパーティション分けされていれば、期間で絞る。直近 4 週・前年の同じ 4 週・12 週 など、仕様が使う期間だけ)。
- 出す先のデータセットは、元の表と同じ場所(リージョン)にする。
- 更新の頻度は、仕様の 1 章の表(SPU・SKU・週ごと・順位は 1 日 1 回、在庫は元の在庫の更新に合わせる、天気予報は予報の更新に合わせる)。

更新は、BigQuery の「スケジュールされたクエリ」で行う。⑦ の SQL をそのまま貼り、頻度を設定する。そのため、出す先のデータセットに書き込む権限(BigQuery データ編集者)が、**実行する人**に要る(CCP のサーバーのサービスアカウントには要らない。CCP は読むだけ)。

CCP の取り込みは、表の最終更新の日時を見て、変わったときだけ読む(`bq_import.py`)。表にすると、ビューのときの `BQ_<名前>_WATCH` が要らなくなる。

## 4. Gemini に渡す前提(組み立て方)

前提は、次の順に並べる。上ほど変わらない内容、下ほど作業ごとの内容。

| 順 | 中身 | どこから |
|---|---|---|
| 1 | 役割と、返す形(下の JSON) | 画面のコードに持つ |
| 2 | 出力の方針(3.3) | 画面のコードに持つ |
| 3 | 出力の仕様: 全体のルールと、その出力の章 | `docs/BIGQUERY_EXPORT.md` の 1 章と該当の章(サーバーがファイルを読む) |
| 4 | 決まりごと・よくある NG | `docs/BIGQUERY_CONVERT.md` の 3 章の 4・4 章 |
| 5 | 手本の SQL | `docs/bq_example/` の同じ出力のファイル(練習用の元データからの変換) |
| 6 | 元の表と列の一覧 | ① で選んだ表の `INFORMATION_SCHEMA`(名前・型・説明) |
| 7 | 元の表の先頭の数行 | ① の `LIMIT 20`(値の形を見せるため。個人情報になりうる列は除く。6 章) |
| 8 | 仕様のまとめ(コンフル) | ② で入れた Markdown |
| 9 | 前の版と、その答え合わせの NG | 直すときだけ |

ポリシーの文書(3.2)は、3〜5 の代わりに `docs/POLICY_FORMAT.md` の全文、6〜8 の代わりに文字にした文書を入れる。

返す形(BigQuery の出力):

```json
{
  "sql": "SELECT …",
  "reasons": ["元の dept_nm を category にした(部門 2 が CCP のカテゴリに近いため)", "…"],
  "questions": ["販売をやめた商品の印が見つからない。…でよいか"]
}
```

前提の長さは、`/api/ask` の上限(40 万文字)の内側に収める。収まらないときは、7(先頭の数行)→ 5(手本)の順に削り、画面に「削った」と出す。

## 5. GCS の文書を文字にする

| ファイル | 文字にする方法 |
|---|---|
| `.md` / `.txt` / `.csv` | そのまま(UTF-8。読めなければ Shift_JIS を試す) |
| `.pdf` | Gemini にファイルのまま渡す(Gemini は PDF を読める) |
| `.xlsx` | シートごとに CSV の形にする(ライブラリ `openpyxl` を足す)。シート名を見出しにする |
| `.docx` | 段落と表を、Markdown の形にする(ライブラリ `python-docx` を足す) |
| Google ドキュメント・スプレッドシートを書き出したもの | 書き出した形式(上のどれか)で扱う |

ファイルを Gemini にそのまま渡すには、`/api/ask` に「文字列だけ」でない入り口が要る(いまは文字列だけ)。開発用の API の中に、ファイルを添える呼び方を足す(CCP の画面の `askAgent` は変えない)。

## 6. 安全の決まり

| 決まり | 内容 |
|---|---|
| 有効にするとき | `CCP_DEVTOOLS=1` のときだけ。既定は無効 |
| BigQuery に投げる文 | dry-run で、文の種類(`statement_type`)が `SELECT` のものだけを流す。DDL・DML・スクリプト(複数の文)は、流さずに止める |
| 読む量 | 試し(⑤)は `maximum_bytes_billed` の上限を付ける(既定 10 GB。環境変数 `DEVTOOLS_MAX_GB`)。全件の確かめ(⑥)は、読む量を見せて、人が押す |
| 返す行 | 画面に返すのは先頭 200 行まで。Gemini に渡すのは 20 行まで |
| Gemini に渡す行 | 名前・メール・電話・住所・レビューの本文のような列は、Gemini に渡す行から除く(列の名前で見分け、画面で外す・戻すを選べる) |
| GCS | 一覧と読み取りだけ。書き込まない |
| 保存先 | `server/devwork/`(`.gitignore` に足す)。利用先の名前を含むので、Git に入れない |
| Gemini の書いたプログラム | 実行しない(最初の版では) |

## 7. コピー・持ち出しのしやすさ

利用者の要望(2026-10-22): SQL をコピーするなど、持ち出しやすくしておきたい。

- **すべての SQL・前提・設定の行に「コピー」を付ける。** 押したら、押した場所に「コピーしました」と短く出す。
- **SQL のコピーは 3 通り**: SELECT だけ / 表を作る形(⑦。出す先の表の名前を入れた形) / コメントなし。
- **コメントを付けて出す。** SQL の先頭に、出力の名前・版・作った日時・答え合わせの結果(NG 0 件 など)をコメントで入れる。コンソールに貼ったあとで、どの版かが分かるように。
- **ファイルで保存。** 出力ごとの `.sql`、6 つまとめた `.zip`(採用の版だけ)。ポリシーは、取り込む形のファイル(`.md` / `.csv`)。
- **出す先の名前は、画面に 1 度入れれば、すべての SQL に入る。** 出す先のプロジェクト・データセット(例: `<プロジェクト>.ccp_out`)と、表の名前の付け方(既定は `ccp_spu` など)を、作業の設定として保存する。
- **前提をコピー。** Gemini 以外(利用先の Claude など)に同じ相談をしたいときに、前提をまるごと持ち出せるように。
- **開発側への報告をコピー。** CCP そのものの不具合に当たったとき、エラーと状況を、利用先の表・列の名前を伏せてまとめる(`<表1>.<列3>` のような置き換え)。それを開発側の Claude に貼れば直せるように。
