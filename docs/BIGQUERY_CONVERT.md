# 手引き: 利用先の BigQuery に、CCP が読む形のビューを作る(利用先の環境の Claude・SQL を書く人向け)

CCP は、[BIGQUERY_EXPORT.md](BIGQUERY_EXPORT.md) の **6 つの出力の形だけ**を読みます(2026-10-20 に販売順位を足した)。利用先の元のテーブルは、列の名前も粒度も違い、スキーマはこのリポジトリと共有できません。
そこで、利用先の環境で、**元のテーブルから出力を作るビュー(SQL)を書き、CCP の道具で値まで確かめる**、を繰り返します。

- 背景: [BIGQUERY.md](BIGQUERY.md) の 11 章
- 利用先のプロジェクト・データセット・テーブルの名前は、このリポジトリに書かないでください(CCP には環境変数で渡します)

---

## 1. 道具

| 道具 | 何をするか |
|---|---|
| [docs/bq_example/](bq_example/) の `*.sql` | **変換の手本**。練習用の元データ(利用先に似せた表)から、5 つの出力を作るビュー(販売順位の手本はまだない。BIGQUERY_EXPORT.md の 9 章の SQL の例を使う)。コメントに、仕様のどの決まりを、どう満たしたかを書いてある |
| `python -m ccp.cli bq-dummy --pack <本番のパック> --yes` | 練習用の元データ(`<dataset>_src`)と、手本のビュー(`<dataset>`)を、BigQuery に作る(開発側の GCP で使う。利用先では使わなくてよい)。**商品は、取り込む先の環境の商品(そのパック)から作る**(別の商品から作ると、取り込みが止まるか、週ごとの実績が入れ替わる) |
| `python -m ccp.cli bq-check` | **値まで確かめる**。設定した出力を読み、キーの重複・必須の空・市場の値・数値の範囲・SKU と SPU の結びつき・データの時点の古さを確かめる。何も変えない。**NG がある出力は、CCP は取り込まない**(取り込みも、同じ確かめを使う) |
| `python -m ccp.cli check` | 列が揃っているか・権限があるか(問い合わせの試し。料金なし)まで |

## 2. 練習用の元データと、手本の対応

手本の元データは、利用先によくある形に似せてあります。自分の環境の元のテーブルに当てはめるときの目安にしてください。

| 元データ(練習用) | 粒度・形 | 作る出力 | 手本で行っている変換 |
|---|---|---|---|
| `m_item` | SKU ごとのマスタ。国のコード `JPN` / `USA`、部門 1(`div_nm`)・部門 2(`dept_nm`)・サブカテゴリ(`class_nm`)、色・サイズ・股下、販売中かの印 | SPU・SKU | 販売中だけ。SKU を SPU にまとめる。国のコード → `JP` / `US`。階層を `category_path` に。部門 2 を CCP のカテゴリに。季節のコード → `autumn` など |
| `t_sales_daily` | SKU × 日の販売。**販売がない日は行がない** | SPU・SKU・週ごとの実績 | 直近 4 週・その前の 4 週・前年の同じ 4 週の集計。週ごとは、商品 × 週の格子を作って 0 を埋める |
| `t_inventory` | SKU ごとの在庫のスナップショット(1 時間に数回、追記) | SKU の在庫 | SKU ごとに最新の 1 行。手元 − 引き当て |
| `t_inventory_hist` | SKU × 日曜の在庫 | 週ごとの実績の `stock` | SPU に合計 |
| `t_pv_daily` | SPU × 日の閲覧数・注文数 | SPU の `views_4w`・`cvr_4w` | 直近 28 日 |
| `t_review` | レビューの明細 | SPU の `rating` など | 平均・件数・最新・本文の直近 20 件 |
| `t_weather_obs` | 市場の代表の地点の、日ごとの天気の実績 | SPU の `lift_*` | 仕様の 7 章(販売がない日も 0。10 日未満はカテゴリの値) |
| `t_weather_fcst` | 予報(出るたびに追記)。天気はコード(100 晴れ…) | 天気予報 | 日付ごとに最新の予報。コード → `sunny` など |

## 3. 進め方

1. **元のテーブルを調べる。** 列の名前・型・粒度・キー、市場(国)の分け方、販売がない日・週に行があるか、販売をやめた商品の印、在庫が履歴(スナップショット)か最新だけか。カテゴリの階層の段の数と、それぞれの値の一覧(`SELECT DISTINCT`)。
2. **出力ごとに、ビューを書く。** 手本の同じ名前のファイルから始め、`{src}` の表と列を、元のテーブルに置き換える。列の名前は、仕様のとおりに `AS` で付け替える(余分な列は無視される)。
   - 順番は **SPU → SKU → SKU の在庫 → 週ごとの実績 → 天気予報 → 販売順位**(順位の `channel` は `all` / `ec` / `delivery` だけ。SKU は SPU に、在庫は SKU に結びつくかを確かめるため)。
   - ビューを置くデータセットは、元のテーブルと同じ場所(リージョン)にする。
3. **CCP の設定に、ビューの場所を入れる**(`server/workbench.env`。見本は `server/workbench.env.example`)。
   - `BQ_SPU` など 6 つ(`BQ_RANKING` を含む): `<プロジェクト>.<データセット>.<ビュー>`
   - **ビューなので `BQ_<名前>_WATCH` も入れる**: 更新を見る元のテーブル(ビューの最終更新の日時は、元のデータが変わっても変わらないため)。在庫なら元の在庫の表、SPU・週ごとなら販売の表、など。入れないと、CCP は 10 分ごとに読み直す
4. **`python -m ccp.cli bq-check` で確かめる。** `[NG]` を直してから、`[注意]` を見る。直しては確かめる、を繰り返す。
   - よくある NG: キーの重複(販売中でない SKU を除き忘れ、結合で行が増えた)、`market` が `JPN` のまま、SKU の `product_code` が SPU にない、`week_start` が月曜でない
   - よくある注意: `category` が CCP の選択肢にない(いまは取り込めるが、表示が値のまま。バックログ B7)、12 週に満たない商品(0 の週の行がない)、データの時点が古い
5. **CCP の画面で取り込む。** 画面を開くと、変わった出力を取り込みます。すぐに読み直したいときは ⚙ →「BigQuery から取り込む」。取り込めなかった出力は、画面の上に理由が出ます(前のデータのまま使います)。

## 4. 決まりごと(仕様の要点)

- 1 行の単位(キー)を重ねない。キーの列は空にしない
- `market` は大文字の 2 文字。CCP の配信カードの国(いまは `JP` / `US`)にない市場は、AI の選定に使われない
- `as_of` は、元のデータの時点(取り込んだ時刻・`CURRENT_TIMESTAMP()` ではない)
- 集計・相関の計算は SQL の中で済ませる。生の明細は出さない
- レビューの本文から、個人を特定できる情報を除く
- 行数が前回の取り込みの半分を切ると、CCP は取り込みを止める(元のデータの不具合を疑うため)。意図して減らしたときは、⚙ から取り込み直しても止まるので、開発側に知らせる
